Lands in one batch with the dependency-key fix (fork PR #910): fork PR #910 first, then this PR after its focused re-check by execution and green CI.

Upstream already holds each subagents tree once per cycle, and this PR carries the follow-up that change names. romp-on/romp PR #1822 (cf0be377f) stores one sample per subagents root, the (directories, stats) pair _subagent_tree answers, on `_live_scope.subagent_trees` for each pusher cycle, jobs pass and connect push, and counts a read answered from a held pair under `scoped`. romp-on/romp PR #1788 is the walk memo underneath it (_SUBAGENT_TREES: a tree validated by one lstat per known directory instead of a listing). The commit message of romp-on/romp PR #1822 names the viewer frame's hit-path re-stats through _dir_stamps as a separate route and a follow-up. The dependency-key defect that romp-on/romp PR #1822 brings (the agent-file walk noted a sibling root under a stat taken after the held listing) is fixed by fork PR #910, which has its own entry, upstream/2026-09-24-subagent-tree-dependency-key.md.

This PR holds the agent-file lookup's re-checks and the launch folds on that scope. Upstream's _subagent_file re-checks a memo hit by stat-ing every directory its walk read, which for a nested agent's file or one found nowhere is the whole tree, and _awaiting_nest folds each awaiting agent's launches once per call (_session_awaiting's and _session_background_items', each through _awaiting_live_rows), several calls per session per cycle, so with nothing changed each call re-stats the tree's directories for every awaiting agent. This PR derives two slots from the held samples. The stamp index, `_live_scope.subagent_stamps`, is filled from each pair as the pair is stored, and _dir_stamp answers a directory it holds with no stat: the memo hit's re-check through _dir_stamps (a viewer frame's among them, when a pusher cycle or a connect push builds the frame) and the walk's stamp of a held root. A directory no held pair lists (the project directory on a miss walk) is stat'd once and that stamp is held for the rest of the scope. The launch folds, `_live_scope.subagent_launches`, fold each agent once per cycle, pass or push; a fold that did not read the file is held for the one call that observed it and folded again by the next. Both slots open and clear at exactly the sites that open and clear `subagent_trees`: the try and finally of _pusher_cycle and _jobs_cycle, and on a connect push _chat_push_scopes_open, which records them as owned before the push's shared read, with _chat_push_scopes_close. So a value derived from a held tree lives exactly as long as the tree and where the tree lives, and a change on disk after the scope's sample, a root's removal included, is seen by the next scope's first read, upstream's one-cycle lag. Of the readers on handler threads, the connect push holds the three slots across its chat loop and viewer frames; the others (a viewer's open, the history and episode replies and the act-now nudge pass among them, the full list in _subagent_tree_memo_report's docstring) hold none and read per call. The measurements that motivated the change, dated 2026-09-19 (a py-spy profile of a deployed kernel with _dir_stamp's os.stat as its top self frame, and another kernel's memo counters), are in tests/test_subagent_tree_stamps_per_cycle.py's module docstring.

The fork's front differs from upstream's in two rules, each with a case that is red under upstream's rule. (i) A sample that reported a fault below its root (a listing, an entry's type or a child's lstat failing for a reason other than absence) is not stored in the scope, where upstream stores any answer with a directory: a held pair reports no fault to a later reader, so the agent-file walk served it would take the unread places for read ones (tests/test_subagent_tree_stamps_per_cycle.py Guards test_a_walk_with_a_failed_listing_is_not_held_while_a_clean_walk_is, and beside it test_a_walk_with_a_failed_listing_by_a_reader_that_passes_no_faults_list_leaves_a_lookup_in_that_scope_told_of_the_fault: an agent-file lookup in the same scope as a reader that passed no faults list walks again and is told the fault, where upstream's rule answers it None with no fault and memoizes the miss). (ii) A root whose lstat fails for a reason other than absence (EACCES from a parent, EIO) raises _SubagentTreeUnreadable from _subagent_tree_sample, where upstream's sample takes every OSError for absence and pops the entry (tests/test_subagent_tree_memo.py UnreadableRoot, an EIO by mock and a real EACCES). Under (ii) the root is neither absent nor held: its readers answer their standing entries unheld or an unreadable marker and the chat build is told to read again, except that with no entry standing the sidecar map answers {} and the agent-file lookup answers a caller that passes no faults list None, so the viewer says the agent's transcript is missing while the fault lasts (ViewerUnderAnUnreadableTree; having the viewer state the fault is a follow-up fix after this change). Those callers are the viewer's two (build_subagent, _subagent_frame_cached), the Agent head's (_stamp_agents) and _subagent_meta's sidecar read, each lasting only while the fault does. The release at an agent's end passes one since this change (fork-only: _release_ended_agents is fork PR #913's code, absent upstream, so an offer drops the sentences that name it or its faulted ends from the texts it carries upstream: the docstrings of _SubagentTreeUnreadable, _subagent_tree and _subagent_file, the cost home's M and faulted-end entries, and the memos.subagentTree paragraph's clause on the release): a lookup that could not be made releases nothing and is made again at the first cycle at which a place its walk could not read reads again, with one read per such place per cycle and no walk until then (a listing that fails past its first entry, or a real-path resolution of the place that fails while its lstat answers, which that read does not see, is looked up at each cycle while it lasts), where before this change the release read the bare None as no file and gave the end up, counted nowhere, and released a standing resolution under the fault with no checkpoint document (tests/test_record_cache_agent_end.py AgentEnd). Two release roads that make no lookup still read a fault on the file's path as the file gone and drop its records with no document, a residual of fork PR #913's code that this change does not close. The feed key's subagents component is the unreadable marker whatever entry stands, so for a fault on the root's lstat present when the key is taken the key moves into the fault and out of it, and an entry derived under that fault is never served after it clears (tests/test_feed_session_memo.py FeedEntryDerivedUnderARootFault; the cost is one derivation of the session's entry at each edge of the fault). Two feed roads stay open, both pre-existing: a fault that begins after the key is taken and clears before the next build moves no component, so the entry derived under it is served after it clears (a residual this PR does not close); and the feed key has no component for an agent's own file, so a launch appended to that file after a build, or a fold that faulted on it with the tree readable, is not seen until another component moves (a follow-up outside this PR). The agent-file walk excludes that tree from its search and nothing else, answering a file found under any other tree (FaultExcludesItsOwnTree), the shape stated once in _subagent_tree's docstring. A fault on the walk's read of any other place it searches (a place below a tree's root, a candidate file, a project-directory entry, the listing) excludes that place alone, the places stated once in _subagent_file_walk's docstring (FaultBelowTheRoot and FaultOnTheWalksOwnRead), and so does a failed resolution of a tree's root or of a candidate in _find_agent_file's containment check, whose two os.path.realpath calls are strict so that a failure raises on every supported interpreter, where unstrict calls raise on 3.10 to 3.12 and answer the path unresolved on 3.13 and later (RealpathFailureIsAFault); and a lookup that excluded a place and found its file nowhere else memoizes nothing, so no miss is memoized under a fault. Nothing failed is held: a missing or replaced root, a stamp whose stat raises and a faulted launch fold leave no entry in the scope.

This PR also records more of the dependency key than fork PR #910 does. Fork PR #910 has the agent-file walk record every directory of each tree it looked through under the stat of the read that answered its lookup, and this PR adds three things. The walk's noted (path, key) pairs are stored with its answer, in the agent-file memo's entry and in the held launch fold's, and a lookup either one answers replays them unchanged (_subagent_file_notes_replay), so every build that looks the agent up records the keys of the walk behind its answer; without the replay, a lookup the memo answers records nothing for the trees its walk read. A walk that noted None for a place whose stamp it took as real (the note's stat or identity lstat failed, or the place changed between them) is not memoized, so no hit replays that None (tests/test_subagent_tree_memo.py DowngradedNoneIsNotMemoized). The memo's hit is validated on each directory's mtime_ns, so under a filesystem clock coarser than an entry change (Linux before 6.13, a filesystem that stamps in seconds) a hit replays keys the walk took before a change made in its stamp's tick until the directory changes again: a residual this PR states and does not close (tests/test_subagent_tree_memo.py CoarseClockTick, its witness; not seen in 15,000 trials on ext4 and tmpfs under a Linux 7.0 kernel). And a path one build reported under two different keys, whose payload then embeds reads of the path in two states, is recorded under _CHAT_DEP_KEYS_DIFFER, a key no stat produces, so the next signature misses and the tab is rebuilt (_chat_build_deps). And the held launch fold records the agent file's own key as the fold's reader stat'd it before its read (the reader's entry, so no stat of its own), reports it to the build it runs in and stores it with the walk's pairs, so every build the fold answers records the file as the fold saw it, whether or not the build stats the file itself: a launch appended between a fold held earlier in the scope and a build that stats the file again (the Agent head's _agent_steps) is recorded as the two keys' disagreement and the next cycle rebuilds the tab, the one-cycle lag the launch-fold slot accepts, and a build that folds the file with no _agent_steps stat of it (a Workflow agent, which has no Agent event in the parent transcript) records the file's key, where before this change it recorded none and a launch appended after it rebuilt nothing until another recorded key moved. The key is the file's (mtime, size), so such a tab is also rebuilt at each cycle an awaited agent's file grows by any record, in the builds whose launch fold ran; for a Workflow agent that is new, since the live row moves with the run's progress description (the phase and label of the agent that reported last) and not with each record (_subagent_tree_memo_report's docstring states the term and its measurement).

dirStats also counts _dir_stamp's stats: each os.stat it takes that succeeds and is not served from the stamp index (the walk's stamps of the own root, the project directory and each sibling root, and the memo hit's re-check), beside the validation's lstats. That joined with this change; before it dirStats counted the lstats alone, so a figure from a kernel without this change and one from a kernel with it are not one series. The population is stated once, at the _SUBAGENT_TREE_STATS comment. The cost, road by road on each loop, on a connect push and on a thread that holds no slot, each term with the executed case that pins it by equality: _subagent_tree_memo_report's docstring.
