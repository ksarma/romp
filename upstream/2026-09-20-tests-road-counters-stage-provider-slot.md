The two stage tests in tests/test_assembly_road_counters.py were red on one worker in every full xdist sweep of the fork's PRs that did not touch the module, and green alone. The cause: kernel/event_model.py holds one process-wide slot for the calling thread's stage-mark provider (_READ_STAGE_FN and _SET_STAGE_FN, set through set_read_stage_provider and set_stage_provider), and every kernel load installs its own _current_read_stage and _set_stage there at module level, so the kernel loaded last in the process owns the slot. The two tests mark the stage on their own kernel's thread-local (the kernel from test_asm_checkpoint.kernel_module(), loaded once per process) and read the count back through the slot, so with the slot pointing at another kernel the rows book `none`. Under xdist every worker collects everything, and the module-level kernel_module() calls in tests/test_intr_marks_memo.py and tests/test_merge_tx_sets_light.py fill that cache at collection, so the module's own kernel installs nothing at test time and the slot stays with the collection's last module-level kernel load. Upstream ships the file byte-identically, with the same unpatched setUp, the same process-wide slot design and both module-level callers, so the slot mixup exists there too. The hazard is LATENT upstream: upstream CI runs pytest serially (python -m pytest -q, no -n), a serial run in the full collection order re-installs the providers through a test_asm_checkpoint.py test before the pair (that file sorts first), and no upstream run shows the red; it would show under xdist, on a worker whose slice holds no test of the nine kernel_module()-calling classes. The change: setUp saves the slot's pair, registers the two cleanups that restore it, then installs this kernel's providers through the public setters, so the slot is this kernel's for the test's length and a later-loaded kernel's own tests are unaffected. Four guard tests come with it: a child process loads the event model and then a kernel under a private name and reports that the slot holds that kernel's pair (the kernel's own module-level install, which the binding would otherwise stop the module from catching); a slot test asserts that while a test of the class runs both halves of the slot are this kernel's and a mark set through the event model's setter lands on this kernel's thread-local; a decoy pair installed through the setters is displaced for the stage test's length and then the slot test's, each run through its own suite, and stands again after each (red in every collection if the binding is removed, a property the original defect lacked; each of setUp's four provider lines deleted alone reds it, the mapping in its docstring); and a raise pin on setUp's order: with the setter install made to raise inside setUp, the saved pair is back in the slot afterwards, which holds because the two restores register before the two installs and fails with the installs first. The module docstring, which grows from 3 lines to 56, records the mechanism and the census beside figures that are this fork's (the sweeps' width and scope, the item counts, chunk and indices at the fork's sha, the four sightings on the fork's box) and is the part of the diff that does not port upstream; _boot_row_parse's docstring, rewritten to point at the module docstring for the premise that the event model is one object per process, would state that premise itself in an offer; the setUp change ports as it is; the four guard tests do not port as they are, since each opens its docstring with this fork's review-round ids and two of them (the decoy test and the raise pin) cite the fork's mutation runs by figure, so an offer would rewrite those docstrings to state the property each pins (a fresh kernel's module-level install takes the slot; both halves are this kernel's while a test of the class runs; a decoy pair is displaced for an inner test's length and restored after it; a raise between setUp's installs still restores the saved pair) without the round ids and the fork's runs. Tests only.
