The project's copy of the module has the same bound (its file differs from the fork's only in how it copies the built bundles), so the same race reds there: the chat sends its tab on its socket and posts it to the shell in the same call, and when the feed's shim hands the kernel's activeChat frame to the page code before the shell's relay task runs, the section moves in the shim's task and the old lower bound (relay <= head) fails by one 0.1 ms clock step although the section moved within the frame. Seen twice in local full sweeps of branches that do not touch the path; not reproduced in 20 runs of the module alone. The fix stamps the shim's handoff from the driver's capture listener (no product change) and bounds the repaint by the first signal and the animation frame after it, which is what the bound checks (the frame, not the task). Two forced-order roads: the kernel's frame first reds the old bound on every run and is green under the new one; the relay first is green under both and keeps the local signal's claim proven with the kernel's frame late. Both start from no pending record: the feed keeps one for each switch it makes until the kernel's echo comes, and a withheld-frame road leaves one standing, so a kernel-first switch in the settle before the kernel-first road used to leave a record that made that road's kernel frame yield. The settle before each road is now followed by a switch whose echo is held until after its relay, which closes any record, and both roads throw at their start if the driver's copy of the record shows one standing. A third road holds the previous tab's echo behind the relay into web and releases the held frames one per animation frame: that frame disagrees with the record the relay left and yields, and the section's head records web alone (no move off web). Tests only, so docs tier.
