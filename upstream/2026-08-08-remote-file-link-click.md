Upstream's `_open_file` is the same swallowed macOS `open`, so off macOS a path click is silently inert — but the deeper problem survives fixing that: `openFile` opens on the KERNEL's screen, which is the wrong machine whenever the dashboard is being viewed from another device, and upstream ships the same remote/`tailscale serve` story. Fix widens `/file` (already serving images + PDF to the browser) to source/text with its own 2 MB cap and a NUL sniff, and routes clicks by host — VS Code editor, or a viewer filling the feed pane on the web. Reuses `fileUrl`, so federated sessions work unchanged; the viewer has since gained its formatting layer (the hljs palette on the feed sheet, sanitized rendered-markdown as the `.md` default, a word-wrap toggle with counter-based numbering). Pure bug fix plus the viewer it needs; no fork-specific content. Note it widens what an authenticated dashboard can read to any text-extension path on the box, which is the tradeoff to flag if this is ever offered. The viewer has since also gained browser DOWNLOADS (`filedl`): `?download=1` serves ANY existing file as a streamed `application/octet-stream` attachment (fixed-chunk writes — `_send` slurps, and a multi-GB file would OOM the kernel), the exists-but-unviewable view case is its own 415 so the client offers Download where a true 404 offers nothing, and the `/remote/<host>/file` relay passes `download=1` through with locally-derived attachment headers. Scope is deliberate (the user 2026-08-09): anything on disk is downloadable — the view allowlist is a rendering choice, not a security boundary, since the dashboard's owner can already read any file through an agent — which extends the same tradeoff above from text-extension paths to everything, the headline caveat if this is ever offered.
