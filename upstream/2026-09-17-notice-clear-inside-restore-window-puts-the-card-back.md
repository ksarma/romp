The pane's Undo restores a cleared card at once from its cache and keeps the id in pendingRestored until a kernel frame carries the card again (feed.ts 4039 at the fold's head; the reconcile in applyFeedPayload, 6459 to 6462, drops the id when a frame carries it and otherwise pushes the cached card back into asks). The three Clear paths (a card's Clear at 1444, an ask group's at 2951, a session's at 4983) add the id to pendingCleared and never touch pendingRestored, so a Clear on a card whose restore the kernel has not yet confirmed leaves the id set: the next frame lacks the card, the clear is confirmed, the unconfirmed restore puts the card back, and the board shows a card the kernel has cleared until some frame happens to carry that id. Upstream ships the same three paths and the same reconcile (f4daa02e2: 1413, 2898, 4913 and 6312 to 6315). The window is the interval between the Undo and the frame that confirms it: on upstream that is the milliseconds before its wake-driven pusher cycle (_pusher_wake.wait(0.5), the cycle at once on a wake); on the fork it is up to PUSH_MIN_INTERVAL_S (1.0 s, the pusher's minimum interval between cycle starts), which a person clicking Undo then Clear can hit. The fix: each Clear path deletes the id from pendingRestored when it adds it to pendingCleared, the bookkeeping the fork's undoClearResult refusal path already does (6651 to 6652; that path is fork-only, from fork commit 28a5abd03, so upstream's fix adds the delete to the three Clear paths with nothing to copy from), with a webview test over applyFeedPayload as the owed test: an Undo, then a Clear before any frame carries the card, then a frame without it, leaves asks without the card. Found by the fork's 2026-09-17 catch-up fold (fixer round c3's triage of tests/test_notice_cards_browser.py, Evidence 4 and the Follow-on section); that module's served driver now waits for the confirming frame before its second Clear and names this entry in its comment, so the pin waits past the defect and does not mask it in code. The fix is a follow-up PR after the fold merges, held; filed by the fold's review round (the fork's PR 756, round 1, Python and shell tests, item 8); the offer waits on the no-new-upstreaming hold like the 2026-09-16 entries, the ledger being the queue.
