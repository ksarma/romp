asyncio.start_unix_server binds and listens at the umask mode, and the chmod to 0600 landed one line later, so hosts/<sid8>.sock stood at the umask mode for the gap: the last member of the create-then-tighten class PR 789 closed for the kernel credential files, found in its round 1 (fresh-5) and split out as its own fix. Behind the owner-only state root, the one guard then, so a window, not a live hole; the umask is not a guard, since the live session host runs at 002, which leaves the group write bit an AF_UNIX connect needs (an earlier draft of this entry named it as one). The fix checks the published path's length against the socket path budget first (sun_path less its NUL, 107 on Linux: a published path over it is one the kernel can never connect to, and the bind's own check moved onto the temp's name once the temp had a name of its own, so at exactly 108 bytes a first cut published an unreachable socket and logged socket-ready), binds a writer-unique temp name beside the published one (the pid and random digits, the published name's length: the published path is the budget on a deep test root, and a fixed temp name was a shared name two hosts for one sid could cross), tightens it by path (fchmod is a no-op on a bound AF_UNIX socket on Linux), and renames it onto the published path, which is therefore born 0600. During its life at the umask mode the temp has one guard, the mode of hosts/, which both creators (the kernel's write_spawn_spec and the host's bind) make and keep 0700 by code through one helper, owner_only_dir, refusing a symlink or a foreign owner and reading a tighten back; each session's hosts/<sid>/ goes through the same helper on both of its creators (the spawn spec and the host's journal), where round 1 had left it on a bare mkdir. The helper closes the static shape; a re-point between its read-back and the path-taking open that follows needs descriptor-relative calls, and the reachable cases need a state root that is not 0700 while a session starts (ours reads 0700 because kernel/judge.py chmods it at import, best-effort, the OSError swallowed, read back once and never re-checked; nothing guards it afterwards).
