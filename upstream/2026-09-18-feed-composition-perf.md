The feed frame (about 8.8 MB on a busy board) goes whole to the feed pane, the Outline and the Waiting-on-you pane, and nothing said what it was made of. memos.feedComposition now carries, per per-entry encode of a frame (the pusher's send stage, the handler-thread cold serve and the cold kernel's first frame), the bytes by component (cards, ledgers and the remainder, the remainder by field for the flag and count fields with every field whose value can carry a string folded into one `other` row at report time) as lifetime sums and the last pass, and per consuming app the bytes it receives today beside what it would receive if sent only the fields its bundle reads (a checked-in table pinned against the webview source; the projections count the folded fields as one, so each is a sum of published rows). The remainder is encoded per field with one encoder and joined into the same sort_keys string, byte for byte; no second encode, no frame change. The card-field and projection estimators run inside their own guard: a raise is counted under `failed`, said once, memoised with the cards so a later hit does not re-raise, and the frame goes out unchanged at every call site. Beside the readers' rows, a phoneFace projection row sizes a frame that does not exist yet, a phone client's feed slot carrying a face per active card (address, title, state, age) plus one summary row per session with a card, so the gap to the phone's cold-open goal is measured before the face frame is designed. Landing is the user's call whatever the tier label, since the block widens what the export carries by kind.

Privacy, in one paragraph. A per-field `by` table published the length of one string for several rows: `selfHost` was sixteen plus the length of the machine's short hostname on every board, a number derived from the machine's name that the export's identifier scan cannot see because it reads strings, not numbers; `working`, `awaiting` and `stateUnknown` were a per-field constant (seventeen for `working`) plus one session name's length when one name was listed; `userTodoRows`, `syncNotices` and `sdkNotices` were the length of one todo's text (which can name an absolute path) or one notice's prose when the board held one; and with the session count recoverable from `order`, `sessions` gave the total length of the session names and repository strings, up to a bounded per-session unknown (a null or fixed-width colour, a null or quoted repository). Dropping or coarsening one row would not have closed this, because `rest` equals the sum of the table exactly, so the same number was re-derivable from the remainder. The fix folds the table at report time by a pinned, checked-in list (FEED_BY_FOLDED), classified by what a field can carry rather than by a fixture's value (judgeLimit included: null normally, but session and host names when the latch is down): selfHost, working, awaiting, stateUnknown, order, sessions, userTodos, userTodoRows, views, viewsFault, judgeLimit, bgServices, clearedForeign, clearNotices, sdkNotices and syncNotices go into one `other` row; the published rows are the five flag and count fields (FEED_BY_ROWS: userTodosOn, dismissedCount, showDismissed, canUndoClear, off), the off frame's four empty federation lists (items, hosts, pendingHosts, pendingDead) and `other`, a fixed set whatever the board; `rest` is still the exact sum of the published table over both `last` and `lifetime`; a key outside FEED_FRAME_FIELDS and the off frame's lists is counted under `other`, so a future field cannot ride into the export by name; the stored tables stay unfolded (the fold is at report time, in one place), and the per-app projections read them but count the folded fields as one: an app that reads any folded field is credited with all of `other`, and only the flag and count rows it reads are added by name, so every published number is a sum of published rows and no difference of published numbers is one folded field's bytes. That last rule closed a second re-derivation the review found: with the projections published as exact per-field sums beside frame, ledgers and the flag rows, frame minus ledgers minus the feed row minus userTodosOn was the userTodoRows row and the Waiting-on-you row minus that minus userTodosOn the sessions row, on every board, so on a one-session board with no repository string the session name's length was published. The rows now over-count the fields an app reads by the rest of `other`, at most the remainder minus the flag rows (about 16 KB against an 8.8 MB frame); a test steps every folded field by one character and holds the set of moved leaves and their deltas equal across the fields, over every integer leaf of the block. Two residuals. First, on a board with no session, no open todo, no tag and no notice the folded row is a constant plus the hostname length and the digit width of views.seq, the same information the frame's whole length has always carried on /perf's send counters and the served body's exact length; with a session the row mixes names, a repository string and ids, and no published number or difference isolates one of them. Second, the base's, for the user's ruling: the card figures are outside the fold. `cards` is the whole per-card strings, and the two card-field estimates (the Outline's row minus the ledgers, `other` and `off`; the `phoneFace` row) are sums of a few fields' lengths over the cards, so on a board with one active card the `phoneFace` row is a constant plus that card's title length and the Outline's estimate that card's title, name, summary and background lengths, sub-sums of the `cards` figure the block publishes whole.
