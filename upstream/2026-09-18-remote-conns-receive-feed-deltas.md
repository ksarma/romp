Since the federated dial terms (8fe70da07, 2026-09-15) the remote dial carries delta=1 and no caps, so a remote kernel serves its feed and its timeline bars on the view-delta slot path ({type:"delta", slot}) after the first full frame. Nothing on the hub side decoded one: the kernel's inline shim reassembles view deltas on its own local socket alone, and federation.ts applied feedDelta for the local host only and had no arm for a slot patch, so a remote Outline, feed or Waiting pane froze after the remote's first full frame (the Outline filed a delta-unapplied row per dropped frame and posted a needSlot the local kernel could not answer: 86 rows in 2.4 minutes on the user phone) and a remote host's timeline lanes froze without a row (timeline-boot.ts drops an unknown type silently). Two halves. The remote dial now announces caps=feedDelta (REMOTE_DIAL_CAPS: the decoder is federation.ts, so the announcement is its own), a remote host's feedDelta applies onto the raw frame held per host and is prefixed whole, and a no-base delta asks the sending kernel for a full frame on its own socket (needFullFeed, held on the conn like needFull and needSlot when it cannot go out). And every remote Conn carries the ViewDeltas receiver VS Code's pipe already used (moved to ui/webview), run on the raw frame before prefixing: a bars patch, and a feed patch from a kernel too old to read the caps term, continue as the reassembled whole frame down the existing arms; one the receiver cannot apply asks the kernel that sent it for the whole slot on its own socket (needSlot), never the local kernel; a patch for a slot this side has no table for is said in a hostconn row and asked for whole, and a patch that finds no base because the slot's whole frame was refused (a collection the receiver's table cannot key) is said in one too, naming the collection, the shape and the remote's build; both rows are said once per event per conn (the reason and the build, not the conn's life), so a redial across the remote's deploy says them again; the unknown-slot row's event is this bundle's (one key per build for every slot it does not decode), so a peer's slot names never widen the latch. So a remote that honours the cap sends feedDelta, one that ignores the cap but honours delta=1 sends slot patches, one that ignores both sends whole frames, and this side applies all three; a bars frame from a kernel before T278c (2026-09-09), whose judging is a flat list the receiver's table cannot key, seeds no base and crosses whole per change, rendered from the flat list. delta=1 stays on the dial: dropping it would make every remote a whole-frame client, a whole bars frame per change (172 KB to 6.24 MB by board, derived for the facts note's lane shapes as uncompressed JSON, not measured) plus the 60 s repost (kernel.py _DEDUP_REPOST_S) per remote host on an idle board, against a bars patch of about 530 bytes (computed from the encoder); the feed prefers feedDelta where the remote reads the term because the slot path re-encodes every card per build on the remote (memos.wire feed_slot_split). The kernel's and read-side doc's enumerations of non-announcing consumers no longer name these sockets. Two refusals from the review (round 6): the receiver refuses a dictlist lane whose name carries the separator, as the kernel's encoder refuses to patch one (seeded, two lanes would merge on the first patch); and the kernel's keyer refuses a byid or dictlist key field that is not a str, so that slot goes whole for every receiver (Python spells 1.0 as "1.0" where JavaScript spells "1", and a receiver keying the whole frame itself held a patched entry beside the seeded one), a cost no producer pays since none ships one. The kernel's inline shim decoder does not mirror the lane refusal and meets only its own kernel, which never patches such a payload: upstream/2026-09-19-shim-decoder-seeds-a-separator-lane.md. Upstream code (upstream/main carries the same remoteDialUrl and the extension receiver, and an upstream hub federating an upstream remote has the same frozen bars and feed); kept in the fork for now, no upstreaming, the user's call.
