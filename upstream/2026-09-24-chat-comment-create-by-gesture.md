In the chat's comment popover, a second comment on the same message, started while the first was still being created, opened with the first comment's words and typed name; the first comment's acknowledgment then deleted the second one's words and swapped its dialog for the first thread; a refused comment's words came back on every passage of the message; and a second send on the message took over the first one's retry hold and working mark. The create id is upstream's own (#1236, which keys the kernel's memo on it). The kernel now echoes it in every answer and announces that it does, in its caps frame (the commentCreateId cap) and on the first strip of every connection (createIdEcho, its connect push). A create dialog takes its mode when it opens: echo mode when its session's host is last known to echo the id, from its latest connection's connect push, the host's caps frame (the local kernel's, or a remote host's own, which federation hands to the page) or its latest create answer, which carries the key only from a kernel with the echo; main mode otherwise. Main mode keeps main's handling exactly, main's frame and its createId included, and so the bug above too (the user's decision). The page records every createId it minted in echo mode: an answer naming one goes to the echo-mode code, and any other answer goes to main's, which touches main-mode state alone, so main's handling sees the answers main saw.

In echo mode the page keys its hold, its working mark and its adoption on the create id, and its drafts on the passage. A sent dialog closed before its answer puts its words in a note until that answer, so a new comment there opens empty; the note shows in a create dialog on any passage of the message, and its words can be selected and copied; words that would overwrite others wait in it too, with Bring it back and Dismiss, and a comment's working mark opens its passage's create dialog. Echo mode posts a comment again only on a connection whose connect push carries the marker, once, so a comment whose answer was lost with the socket is settled by the answer to its re-post (the kernel's repeat memo keeps that to one thread while the thread is open, among its latest 256 creates, and until the kernel restarts; past those limits the re-post makes a second thread, or, for a comment whose landed thread still holds its typed name, is refused as a name clash, its words back in its dialog or in the note as not saved); nothing is posted again before a connection's connect push, while the page's own socket is closing, or from a strip that a dropped socket left in the page shim's queue, which the shim's socket number tells apart. A late ack for a comment the page gave up on settles it as main's late ack does. The popover saves a size only when the person resizes it. A main-mode dialog with nothing in its note has main's DOM.

The fail-safe (the user's decision, 2026-09-28), for a comment sent in echo mode that is still being sent when its kernel restarts as an older version: when the page finds a connection without the echo (a connect push without the marker, an answer without the key, or a caps frame without the cap), each echo-mode comment still out on that host stops being handled, with no retry, no re-post and no conversion to main's handling. Its dialog closes, and its words and typed name wait in the note, which says the comment may or may not have been saved because the kernel restarted as an older version, with Bring it back at once. An echo-mode dialog open there that has not sent turns main mode, its typed words in its note. The residual, in the person's terms: the page posts nothing more of the comment. It may be saved already, if the kernel with the echo saved it before it restarted and its acknowledgment was lost with the socket, and the older kernel may still save it if the comment reached that kernel (one sent between the connection's open and its connect push, or one the page's shim queued while the socket was down or closing and sent first on the new socket); a comment no kernel saved is saved only when the person brings it back and sends it. A comment a kernel saved shows its thread beside its note entry until the person dismisses the entry, and bringing it back and sending it makes a second thread, which the person can delete. The older kernel's acknowledgment of a comment it saved carries no create id, so main's handling takes it, as on any kernel that never announced the echo (the user's decision, 2026-09-25): it deletes main's draft of the message and swaps a main-mode create dialog open on that session for the comment's thread, so words the person brought back from the note and then changed are cleared, with no notice that the comment was saved, as main's handling clears a create dialog's words when another comment's acknowledgment arrives. A second residual: a comment posted again when its connection comes back, while its first post is still being created in the kernel, stays busy until the next change in its session (the comments frame that lists its thread names no create, so the page cannot settle it from that frame without guessing).
