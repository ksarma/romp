Handler._send adds Cross-Origin-Opener-Policy: same-origin to every response it builds, and a send_error override adds it once to the refusals http.server writes itself: the 414 for a request line over 65536 bytes, which a page on another origin can open as a top-level document with a long URL, the two 431s, the 501, and the 400 for a request line of four or more words whose last is a well-formed version below HTTP/2.0 other than HTTP/0.9 itself. A page on another origin that opens a dashboard page with window.open keeps a handle to it, and the handle is what lets that page post it window messages; under same-origin a top-level document the kernel serves starts a browsing context group of its own, so that opener gets a closed handle and the page has no opener. The dashboard's own tabs (a /file image or PDF it opens with window.open) are documents on its origin with the same policy, so window.open still returns a handle and the in-app view does not take over (preview.ts openFileTab reads only whether it got one). Browsers enforce the policy only on secure contexts (https, localhost) and read it on document navigations only; on a plain-http tailnet address it is ignored, and the sender checks in the pages' own listeners (upstream/2026-09-24-chat-handler-foreign-sender.md) are the defence everywhere.

The override sets a flag around super().send_error(), and end_headers adds the header only while the flag is set, since send_error writes its headers there and _send writes its own copy: a response with two copies of the header leaves a browser with no policy. Not covered: a request line of at most 65536 bytes whose version is missing, malformed (a word after the version makes it so), HTTP/0.9 itself, or HTTP/2.0 or later gets every reply in HTTP/0.9's shape, with no status line and no headers at all: http.server's refusals (its 400 and 505 for the line, and its 431s and 501 for a line that gets past those) and the kernel's own reply to the request alike, the page itself for a GET (a bare `GET /chat` is answered with a page and no headers); no browser sends one. A line over 65536 bytes is not among them: http.server writes the 414 before it parses the line, so that line gets the full 414, the policy included, whatever version it names. So the 431s and the 501 carry the policy only on a request line whose version is below HTTP/2.0 and not HTTP/0.9, which gets a full reply, the policy included. The responses written with send_response directly (the /file and relay HEAD and range replies, the downloads, the CORS preflight and the socket upgrade) carry no policy; none of them is a document.

fix tier: tests/test_kernel_auth_hardening.py OpenerIsolation reads the header off a live socket, bare and under each navigation's request headers, session cookie and, on /file, cap (tests/document_navigations.py), on the shell, every pane page, the sign-in page on / and on /login, an asset and each document shape the /file route builds, and requires exactly one copy; test_each_refusal_http_server_writes_itself_carries_it_once reads each of the six refusals once off the wire, with no navigation's headers or cookie, and requires exactly one copy: the 414, both 431s, the 501 and two 400s (a request line ending in HTTP/1.1 and one ending in HTTP/0.5), the 431s and the 400s over a raw socket; test_a_request_line_over_65536_bytes_gets_the_full_414_whatever_its_version reads the 414 to a line over 65536 bytes in seven version forms, the forms answered with no headers when the line is shorter among them, and requires one copy on each; tests/test_kernel_remote_file_relay.py covers every shape the /remote relay answers through _send; OpenerIsolationWireWitness shows that a second copy written in send_response or in end_headers reaches the wire as two. Without the header line in _send, OpenerIsolation, the relay's opener tests and the witness fail; without the override, the refusal test fails on each of its six refusals and the 414 test on each of its seven forms. In Chromium, Firefox and WebKit, a page on another origin that opens the 414 gets a closed handle and the error page has no opener; without the override the handle stays live and the page keeps its opener.

Upstream's main (f4a572008) sends no opener policy and has no send_error override; Handler's lines around both hunks are the same there, so the change applies there as it is.
