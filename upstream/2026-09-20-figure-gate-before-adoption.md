The viewer fetched a gated figure while its placeholder said "Click to load". The review of fork PR 862 found it on main for an HTML img in WebKit (finding extra8-3, two refuters, a pre-existing defect); the review of this branch found it for an inline svg image in Firefox and in WebKit. mdBlock adopted the sanitized nodes into a live-document element before the figure chain ran. WebKit starts an img's fetch synchronously when the element's node document becomes one with a render tree; for the img figures, the servers' logs held no line in Chromium or Firefox before the chain ran. An inline svg's image is loaded by another path: at the base Firefox requested a gated one, spelt href or xlink:href, while its placeholder stood when the chain's work between the adoption and the gate was long (the second leg's 3000-paragraph note, both spellings, 3 of 3 runs; shorter notes in some runs or none; the counts are under "Run counts, the svg vectors" in the plan section), WebKit requested the xlink:href spelling in every run and the href spelling in none, and Chromium requested neither. The fix runs the whole chain over DOMPurify's RETURN_DOM body, a DOMParser document with no browsing context in which nothing loads, and adopts afterwards. Upstream ships the viewer, so it is a candidate; a privacy surface, so it lands on the owner's word.

Reachable from the kernel-served dashboard, in Safari and in Firefox (Chromium requested no gated figure at the base through any vector measured), and from the iOS web app, which is the same page in Safari's engine; not from the VS Code panes, whose CSP allows no remote img-src. What left: the reader's IP address, the time, the user agent and the figure's path, with no Referer, since the kernel sends Referrer-Policy same-origin. A figure of the file's own folder was also requested against the page, as the attribute read before rewriteFigureSrcs repointed it, and then again through /file. Two legs read real servers' request logs through a proxy the test runs, never page.route, in Playwright's Chromium, Firefox and WebKit. file-view-figures-gate-adopt-browser.test.ts, an HTML img in three scenes (a figure on an unlisted host, a figure of the note's folder, a document opened from its URL with an absolute and a protocol-relative remote figure): red in WebKit at 2d41e5c9b in all three scenes, green in Chromium and Firefox there. file-view-figures-gate-adopt-svg-browser.test.ts, two inline svg images at the end of a 3000-paragraph note, one spelt href and one xlink:href, a host each: red in Firefox (both requested while the placeholders stood) and in WebKit (the xlink:href one) at 2d41e5c9b, green in Chromium there. Both legs green in all three engines after the fix. Both skip in CI, whose npm test runs before its one browser install; file-view-figures-gate-adopt.test.ts runs there, driving the real viewer under plain node over an inert and a live document and pinning that no node entering the live document, at any depth of the viewer's box, carries a fetching attribute on an unlisted host or page-relative, that no live write of one lands during the render and that none stands under the box once the render is done, red on the base's order and on three other mutations in scratch copies of the head, green at the head.
