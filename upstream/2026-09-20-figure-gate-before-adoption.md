In WebKit the viewer fetched a gated figure while its placeholder said "Click to load", a pre-existing defect on main found by the review of fork PR 862 (finding extra8-3, two refuters). mdBlock adopted the sanitized nodes into a live-document element before the figure chain ran, and WebKit starts an img's fetch synchronously when the element's node document becomes one with a render tree; in Chromium and Firefox the servers' logs held no line for the figure before the chain ran, so neither leaked. The fix runs the whole chain over DOMPurify's RETURN_DOM body, a DOMParser document with no browsing context in which nothing loads, and adopts afterwards. Upstream ships the viewer, so it is a candidate; a privacy surface, so it lands on the owner's word.

Reachable from the kernel-served dashboard under WebKit (Safari, and the iOS web app, which is the same page in Safari's engine); not from the VS Code panes, whose CSP allows no remote img-src. What left: the reader's IP address, the time, the user agent and the figure's path, with no Referer, since the kernel sends Referrer-Policy same-origin. A figure of the file's own folder was also requested against the page, as the attribute read before rewriteFigureSrcs repointed it, and then again through /file. The leg reads real servers' request logs through a proxy the test runs, never page.route: red in WebKit at 2d41e5c9b in both scenes, green in Chromium and Firefox there, green in all three engines after. The engine measured is Playwright's WebKit build, not a device; the iOS statement rests on the shared engine. The record is the section "Fix: the gate before adoption (2026-09-20)" of plans/markdown-viewer.md.
