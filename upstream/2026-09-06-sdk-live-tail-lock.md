title: The SDK live tail has a lock, and a handler failure on one streamed SDK message no longer ends the session's CLI. **The lock:** `SdkBackend._live` (sid → {message uuid → atom}) is shared by the kernel thread (send, recall, dismiss, the pusher's `live_atoms` / `prune_live`) and each session's loop thread (`_forward`, the settle's `retire_live_work`, `_mark_dropped_echoes` at spawn and reconnect) and had no lock: `KeyError: '<message uuid>'` from a sweep reading `d[k]` off a stale key list closed a session's CLI mid-work (killing a Workflow run and a background agent, 2026-09-06); `_persist_echoes` raised `RuntimeError: dictionary changed size during iteration` out of the pusher's whole chat build (every client missed the cycle, nothing reached the error center); `_mark_dropped_echoes` raised it out of the session thread at reconnect, outside the connect's try (the thread died with no reconnect); and the two-step `if not d: _live.pop(sid)` orphaned an atom stashed between the steps (an input echo gone from the chat and from `reg['echoes']`). One `RLock` (`_live_lock`) now guards it: every stash (`_stash_live`, `_forward`), every pop, the sid-level pop and every iterating read take it; sweeps walk a snapshot taken under it; the emptiness check and the sid-level pop are one step; it is never held across I/O or a callback (`retire_live_work` snapshots, salvages outside, pops from the same dict object back under it). Cost on the pusher path: +0.5 µs per `live_atoms`+`prune_live` on a 100-atom tail (26.6 → 27.0). **The containment:** the receive loop (`SdkSession._drain`) runs each message through `_handle_stream_message`, which logs the exception type, the message type and subtype, the exception's text (uuid-shaped ids shortened, 160-char clip), what that message lost, by its shape (a transcript record is kept — a compact boundary is one, a control request's command-output line is not; a ResultMessage's turn still settled, or did not, read from the settle's own marker rather than assumed; a stream-only frame's content is gone) and a frame chain bounded from the OUTER end (at most the innermost 8 frames and 600 chars, dropping outer frames first, so the failing frame is always kept; a RecursionError's ran to 18 KB) and continues; the reporter is guarded (a failing `__str__` or log callback cannot end the stream); the ResultMessage branch is ONE try whose `finally` is the whole settle (the state resets, 'waiting', the turn-end count, the queue wake, the poke, the rename ping, the deferred reconnect), so a raise anywhere in the result's bookkeeping — the spend fold on a NaN usage field, a failing spend write — still closes the turn, and the settle's own failure reports are guarded, so a raising log callback cannot replace the bookkeeping's exception in the containment's report; repeats of one (session, exception type, failing frame as file/line/function) count on one error-center entry with one feed-cache bust (`_log`'s `key=`) and re-enter with the full line once the ring has evicted the entry; a fault of the stream itself still ends the loop, logged with the failing task and its frame chain. **The reconnect hold** (pre-existing on main, found by the round-3 review of the settle): `inputs()` holds the queue while a reconnect is armed (`_reconnect`). The settle woke the feeder and then armed the deferred reconnect, both wakeups FIFO on the loop, so the feeder fed a message gate-held behind an interrupted turn to the client about to be torn down; the teardown stranded it in flight and `_reconcile_stranded`, on a resumable conversation, flagged it 'never delivered', so the user had to resend. Now the new client's feeder takes the head; the same hold covers the idle arm in `_do_request_reconnect` racing a send. It keys on the armed flag only, so a pending `/effort` change does not stop mid-turn forwards
