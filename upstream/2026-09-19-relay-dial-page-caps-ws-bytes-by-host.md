Part 1 is the remote client half of the reconnect design: a remote redial declares the pair its conn's own bases hold, held:feed:<gen>.<rev> from the pair beside the raw feed base and held:bars:<gen>.<rev> from the receiver's bars base, beside the decoder word feedDelta and never from the page's caps string (the page's held member is its LOCAL kernel's pair, and its hold words readyGate and chatResume are holds on its own socket). connect()'s per-dial reset is gated per base, so a base a stamping kernel left a generation on survives the redial and a base holding none is reset as before; the bars receiver accepts a composed frame (one carrying through) at any rev at or above its base, the caught-up resume included; a stamped feedDelta applies under a gen gate (gen equal, base at or below the held rev, its through, which every stamped delta carries, at or above it) and a refused one asks for the full carrying the held pair, while a feedDelta carrying no gen applies on the base's presence alone and moves no pair, the vintage guard revision 11 of the design states as its clause (2). A gen is the kernel's string (its boot token and a counter joined by '-', holding neither '.' nor ','); the client reads any other value as no stamp. Every kernel in this repo stamps no gen, so every remote redial stays undeclared until the kernel does; the served labs derive a dial's caps from the frames the host's earlier sockets received, and record caps=feedDelta on every dial. The declaring-dial leg and the two-kernel redial lab live in this PR in skip-and-branch form: the leg skips only when no served frame carried a gen key and fails when one did but no pair parsed, the lab branches on the same read, each counts the composed frame by newGen and never by through, and both read the K2 counters as the flat keys resume.feed.adopt and stash.evict.undeclared under GET /perf memos.wire, the serialization the K2 kernel PR must match. Part 2 is the field the fork's owner approved on 2026-09-19 by name (the bytes each attached host sent, one number per host, no content): counted in the conn's ws.onmessage before the parse in the shim's unit (String.length, keepalives and undecodable frames included), kept per page-lifetime host position (h1 the first remote host the page saw, never pruned on detach so a re-attached host keeps its position and the collector's per-minute difference stays right), one key per attached host, no cap; a position is on a row while its host is attached at the flush or received characters in the minute, so the row closing a detach's minute carries the host and the rows after it do not, and the field is absent when no host is attached and none received. The map's keys carry positions and no host name; positions are per pane document (one federation manager each). Host names reach the file wherever an admitted value can hold one, in three forms: a bare name under a host key (the shell's push-test row, federation's hostconn rows and the kernel's own wsopen row for a spliced relay, written by _note_ws_open); a host-prefixed session id, <host>:<uuid>, when the row concerns a remote session (the chat surface's sid, id, ids and active, filed on routine use, older than this field and not gated by the share switch, so the most frequent host-carrying row type on a federated page); and a host-keyed map (federation's feedmerge counts). The position-to-name map follows from the rows that record a host at attach (federation's hostconn open rows of the same pane), not from chat rows alone; GET /tunnels (the authenticated route whose row order assigns the positions, re-derived at every page life, so an unchanged roster gives a host the same position after a reload) and the state directory's host registries beside the file, remotes.json (the live set) and remotes-known.json (the detached hosts), are position-to-name maps in their own right, with no client-diag row; reading one is itself a join, exact for a pane life that attached one host and an order inference for several, holding while remotes.json still carries the order the pane's /tunnels answer had. tests/test_client_diag_allowlist.py classifies every admitted key of every surface by the content its value can carry, so a new key fails there until classified. No /perf aggregate, export or public projection reads client-diag, and romp perf client folds by explicit .get() and never reads wsBytes.
