Part 1 is the remote client half of the reconnect design: a remote redial declares the pair its conn's own bases hold, held:feed:<gen>.<rev> from the pair beside the raw feed base and held:bars:<gen>.<rev> from the receiver's bars base, beside the decoder word feedDelta and never from the page's caps string (the page's held member is its LOCAL kernel's pair, and its hold words readyGate and chatResume are holds on its own socket). connect()'s per-dial reset is gated per base, so a base a stamping kernel left a generation on survives the redial and a base holding none is reset as before; the bars receiver accepts a composed frame (one carrying through) at any rev at or above its base, the caught-up resume included; a stamped feedDelta applies under a gen gate (gen equal, base at or below the held rev, its through, which every stamped delta carries, at or above it) and a refused one asks for the full carrying the held pair, while a feedDelta carrying no gen applies on the base's presence alone and moves no pair, the vintage guard revision 11 of the design states as its clause (2). A gen is the kernel's string (its boot token and a counter joined by '-', holding neither '.' nor ','); the client reads any other value as no stamp. Every kernel in this repo stamps no gen, so every remote redial stays undeclared until the kernel does; the served labs derive a dial's caps from the frames the host's earlier sockets received, and record caps=feedDelta on every dial. The declaring-dial leg and the two-kernel redial lab live in this PR in skip-and-branch form: the leg skips only when no served frame carried a gen key and fails when one did but no pair parsed, the lab branches on the same read, each counts the composed frame by newGen and never by through, and both read the K2 counters as the flat keys resume.feed.adopt and stash.evict.undeclared under GET /perf memos.wire, the serialization the K2 kernel PR must match. Part 2 is the field the fork's owner approved on 2026-09-19 by name (the bytes each attached host sent, one number per host, no content): counted in the conn's ws.onmessage before the parse in the shim's unit (String.length, keepalives and undecodable frames included), kept per page-lifetime host position (h1 the first remote host the page saw, never pruned on detach so a re-attached host keeps its position and the collector's per-minute difference stays right), at most four positions named and the rest under hmore; a position is on a row while its host is attached at the flush or received characters in the minute, so the row closing a detach's minute carries the host and the rows after it do not, and the field is absent when no host is attached and none received. The perf minute row carries positions, never names; the file's shell and federation surfaces and the kernel's own wsopen row carry host names already under their host key (the shell's and federation's under an earlier approval; of the kernel's four direct writers only _note_ws_open writes it, the host a hub's spliced upgrade was relayed to), so a reader holding the perf row and any of those three can map a position to a name within one page life. No /perf aggregate, export or public projection reads client-diag, and romp perf client folds by explicit .get() and never reads wsBytes.
