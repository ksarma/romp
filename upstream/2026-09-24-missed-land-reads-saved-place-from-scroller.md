Upstream's landActive writes the view's saved place raw when a land misses: render.ts line 14055 at upstream's 3a5f50406, `else writeScroll(content, v.scrollTop, "land-saved");`, the same text as line 15125 of the fork's main before PR 861 (and the same line at 380a94048, a later upstream main whose ui/ tree is unchanged). On the session already on screen the saved place lags the scroller by one frame after a page write that does not update it (the re-window's, in virtualizeToViewport), so a deep link whose land misses inside that frame, with no pre-jump in the attempt to update the saved place (every link with no time is such a link), writes the reader back a frame: from 8 to 0 in the landing lab, which leaves the viewport top above the first element that names a turn. The fix: showActive decides before the display flip whether the scroller holds the view's reader (the view already displayed, in a visible pane, with no deferred build pending) and hands that to the synchronous land alone, and landActive then syncs the saved place to the scroller before its capture and before the raw write. The witness is the landing lab's road 16 in tests/test_landing_notice_browser.py, whose second deep link carries no time and lands inside that frame on every run: with this PR's lab file copied over each tree (road 16 there as at the head), under Chromium, it is red in 3 of 3 runs over upstream at 3a5f50406 and in 3 of 3 over the fork's main before PR 861 (0 != 8, the writes land-guess to 0, rewindow 0 to 8, land-saved 8 to 0, ending at top 0 with no turn under the viewport top), and green in 3 of 3 at this PR's head.

PR 861 (upstream/2026-09-19-chat-tail-compact-incremental.md) moved the missed-land fallback to a restore of the row captured at the saved place before the attempt. That carried the same lag onto a link with a time, whose pre-jump had updated the saved place before the old raw write read it: the landing lab's road 10, which failed now and then in the fork's CI after PR 861 landed. That extension stays in 861's entry, with the pins that 861's restore on a fetch-armed miss leaves a reader scrolled up in history at their place. Upstream has only the older part, so an offer would carry showActive's decision, landActive's sync and road 16; the unit roads live in land-active-keep.test.ts, which only the fork has. A deep link on the view already on screen whose build is deferred (compact mode with changed events) still reads the saved place, which can lag the scroller, because the pending build keeps scroll events out of it; no road reaches it, and upstream's showActive has the same deferred path, so an offer carries this residual too. Whether this is offered upstream is the owner's call.
