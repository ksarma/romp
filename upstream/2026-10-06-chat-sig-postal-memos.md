While a dashboard is connected, every cycle checks each cached chat tab's signature, and the postal part of that check walked every postal card of the tab again (_postal_card_deps), reading each card's caption, its peer's name and colour, and for an outgoing card the colour by name through a linear scan of the names snapshot. The walk's answer moves only when one of its inputs does, so it is now memoized on the tab's dependency record, keyed on a digest of the thread's names snapshot taken in the snapshot's order (a by-name colour is the first entry carrying the name, so order matters when two entries share one), the postal index object (rebuilt exactly when the log moves while a log exists; with no log each check gets a new empty one and walks) and, for a record whose cards carry a message id, the caption map object, which is still fetched every cycle for such a record (a record with no message-id card never fetches it and is not keyed on it). With no names scope (a thread outside a push) nothing digests the names and the walk reruns on every check. The by-name colour reads an index built once per names digest. The re-profile's offline A/B of a sketch of these two memos (30 tabs, 25 interleaved rounds) measured a no-change push at 266 ms before and 197 ms after, with identical signature tails on every tab. That gain holds only in cycles where no discovered session writes. A transcript append, a pending cut, or a write to a session's states file, captions file or goal store moves that session's caption key, and `_msg_summaries` then publishes a new union dict whether or not a caption changed, so the postal memo misses on every tab whose cards carry a message id. A bench of this branch measured about 54 ms saved per push (30 tabs) in cycles where no session wrote, and about 21 ms, the colour index's share alone, in cycles where one did, which in practice is every busy cycle. The re-profile's live estimate shrinks to match: cycles of 2 s or more about 2% shorter, not 5%, and about 0.01 cores is an upper bound, reached only in cycles where no session writes. Tests: a second cycle with unchanged inputs walks no card (red before: two walks), the snapshot is walked once per digest rather than once per card (red before: one walk per card, 41 for 41 cards), and the signature tail equals an unmemoized check byte for byte across names added, renamed and recoloured, cards added and removed, captions changed, the log moved, two entries sharing a name in both orders, an empty registry and no names scope. Further tests pin what the memos rely on: with no names scope every check walks the cards and a rename between two checks reaches the tail; the digest cache and the record's entry hold the snapshot, the index and the caption map themselves, not their ids (alternating registries and caption maps replaced twice per check, each tail equal to the unmemoized one); a thread that asks while another is building the colour index never answers from a part-filled one (staged deterministically); and the real `_names_snapshot` and `_msg_summaries` return a new object on every call or change and never edit one they returned, and fed into the signature give the unmemoized tail. A record whose cards carry no message id walks once across three cycles with the caption map replaced before each and never fetches it (red before: a walk every cycle; red under a memo that fetches the map on every hit, or whose entry always claims a message id). And every dimension of each key has a pin that changes only that dimension and holds the tail against the unmemoized check: the snapshot object for the digest cache; for the names digest that the colour index and the record's entry share, the entries' session ids (an entry moved to another session id, and two swapping theirs), names, colours, order, working directory and later fields; the index; the caption map; and the record. Each pin is red when its dimension is dropped from that key: on a stale value where a reader reads the dimension, and on the miss alone for a field no reader reads (the working directory, the later fields, and the session id for the colour index).

The project's public tree (upstream/main, last updated 2026-09-24) carries the same `_postal_card_deps`, `_name_color_by_name` and `_chat_sig_deps`, identical to the fork's before this change (compared by AST, docstrings included), and its `_names_snapshot` builds a new snapshot dict on every call as the fork's does, so the per-cycle walk and the per-card scan run there too. Its `_msg_summaries` publishes a new union dict whenever it rescans a discovered session or one leaves discovery, and `_postal_index` a new dict when the log's key moves, the identities this key relies on. Not run against that tree.
