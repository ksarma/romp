The class, found by execution on the text upstream landed from the fork's offer 1847: a git read whose output the hook greps fails (a non-zero status, or an error line) and the hook reads the failure as an empty result, so a failed scan passes as a clean one. The first instance was the annotated-tag arm (a cat-file -p failing while cat-file -t still said tag let a tag whose tagger domain was on the denylist through a real push, nothing printed, every counter at zero); the round after it found the same road under the tip's content grep, its symlink listing, each link's target and the tag TYPE read, each letting a tip that only inherited a leak through a real push. The fork's fix routes every such read through one helper (unscanned) that prints a line naming the ref and the read and sets failed_scan, the refuse-on-unscanned road the gitleaks arm already owned; the value still counts as empty so the scan goes on to its verdict, and an ABSENT value (a tag with no message, a tree with no links) still reads as empty and passes. One offer for the class, with the population below. It waits on the user's decision whether to report it upstream.

The population, each read with its disposition. Line numbers are the hook's at fold 3 HEAD 9ee54fd6b, before the round f4 edits. The probe harness: the fold 3 tag probe (fold3/tagprobe.md in the upfold notes: a scratch HOME carrying a synthetic denylist, a bare remote, the hook fed its stdin line directly and through a real push with GIT_EXEC_PATH pointing at a git shim that fails ONE subcommand shape and execs the real git otherwise), copied per road for the round f4 probe logs probe-grep244.md, probe-lstree259.md, probe-revlist274.md and probe-catfilet311.md, and the fixer log fix-f4-prepush.md.

- chosen_emails, `git config --get-all user.email || true` (line 165): SAFE by assessment, not probed. A failure leaves the chosen list empty, so every stamped address is scanned: over-scan, never under-scan.
- the annotated-tag arm, the TAGGER, MESSAGE and OBJECT reads (lines 312, 323, 331): reachable (cat-file -p failing while cat-file -t succeeds) and fail-open; FIXED in round f3 (tag_unread), the message captured before its grep.
- each link's target, `git cat-file -p <blob>` (line 263): the tag arm's twin, ruled in without a probe; FIXED in round f4. The real-fault shape (a loose blob removed from the store) is pinned by the bats case that once asserted the fail-open.
- the tip's content scan, `git grep -l` over the tree (line 244): PROBED reachable (a git grep exiting 2; a blob missing from the store, which git grep reports on stderr and skips, exiting 1 or 0; a blobless partial clone with its promisor unreachable, exit 128; a killed process; an argument list too long) and fail-open (a tip that only INHERITED main's leak, which no other pass reads, went through a real push). FIXED in round f4: the status and the error stream are read apart from the hits, and a status above 1 or any non-hit line refuses.
- the tip's symlink listing, `git ls-tree -r | grep '^120000 '` (line 259): PROBED reachable (one subtree object missing: ls-tree listed the link, exited 1, the pipeline took grep's status, and a real push published the branch) and fail-open. FIXED in round f4: the listing is captured before the grep, a failed listing refuses, and whatever it did list is still read. A pushed object that peels to a BLOB (a tag of a blob) has no tree, so its listing is absent, not unreadable, and passes; git grep names a hit in that blob by the bare sha, read as a hit (the round f4 audit).
- the commit list, `git rev-list <range> || git rev-list <tip>` (line 274): PROBED reachable (a remote-tracking ref whose object is missing; an unfetched remote update; a corrupt loose commit in the range) and FAIL-CLOSED. The half fault (the range fails, the fallback works) scans the tip's whole history: over-scan. The full fault ends the hook under errexit at the assignment (exit 128, no verdict, nothing publishes). NOT edited in round f4, by the round's rule (fix only what is reachable AND fail-open). For the follow-up: the refusal rests on errexit alone and prints no hook line and no failed_scan; the probe's shape is `if ! revs=$(...)` with an unscanned line, so the tag arm and gitleaks still run and the verdict gate refuses.
- the tag TYPE read, `git cat-file -t || true` in the peel's loop test (line 311): PROBED reachable (a shim; and any single child failure, a fork refused under a pids limit or a killed child, since `|| true` turns every status into "not a tag") and fail-open (the pushed tag was never peeled or scanned and a real push published it; an inner tag under a clean outer one likewise). FIXED in round f4: the kind is read apart from the loop test for the pushed object and for each one the peel reaches (type_unread), and a branch tip's line does not call it a tag.

Seen in round f4 outside the ruling's population, unprobed and unfixed, for the same offer: the per-commit reads (added_lines piped into grep at line 277, the message `git log | grep` at line 295, stamped_addresses' `git log | while read` at line 188) take grep's or the loop's status, so a diff-tree or log that fails reads as a commit that adds, says and is stamped with nothing. Git's own error line is not suppressed there, so the failure is visible on the terminal, but the push is not refused for it. Observed once by execution: with a link's blob removed from the store, the link commit's diff-tree failed with "fatal: unable to read" and its added-lines pass read as no hit; that push was refused on other grounds (the tip scan's unread-target line and a leak elsewhere).
