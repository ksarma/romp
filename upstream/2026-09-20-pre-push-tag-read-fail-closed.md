The fix, in the fold (review round r1; the rule: stop inferring "clean" from exit 0, which says gitleaks reported no finding, not that it scanned; require positive evidence of coverage and refuse without it). The hook captures gitleaks' stderr, its log, apart from its stdout (the findings still stream live to the hook's stderr through a third descriptor: `log=$( { "$gl" git ... 2>&1 1>&3; } 3>&2 ) || rc=$?`), re-emits the log, keeps the exit-status arms (1 or above 2: failed_scan and failed_creds as before; 2: a finding), and when gitleaks CLAIMS a scan (exit 0 or 2) applies two independent conditions to an SGR-stripped copy of the log: (1) any line at its ERR level refuses, `the CREDENTIAL scan of <ref> (<sha10>) did not complete: gitleaks logged an error (<the first ERR line>)`, failed_creds=1; (2) the reported `<n> commits scanned.` must equal the hook's own count of the commits with content to scan, `covered <reported> of the <expected> commits with content to scan` on a mismatch, `reported no commit count, so what it read is unknown` when the line is absent, failed_creds=1 on each. Two conditions because either alone has a hole: the short mode writes no ERR line, and an aborted scan can report the whole count. The expected count is derived by a new helper, scannable_commits, over the SAME `git log -p -U0 --format='commit %H' --diff-merges=first-parent` stream by gitleaks' own rule (a commit counts once a file that is neither deleted nor binary has a hunk; gitleaks' sources for v8.30.1 and v8.28.0 read: one `addCommit` per fragment, a fragment one hunk of a non-deleted non-binary file, the count the distinct shas), because `git rev-list --count` over-counts every empty, delete-only, binary-only, mode-only or rename-only commit and every merge with an empty first-parent diff (nine of 22 shapes disagree with gitleaks; the derivation agrees with both gitleaks versions on all 22 and on a 4556-commit range of the fork's own history, 4544 both). The same stream, but not the same bytes: since the round's audit both reads ask git for a plain stream, `git log --no-color` in scannable_commits and `--no-color` appended to gitleaks' `--log-opts`, because a transform the clone's configuration applies to the stream reaches both readers alike and a count that agrees with an emptied scan is no evidence (the colour road, below). The derivation's own failure is its own road, read before the scan: `expected=$(scannable_commits $range) || { rc=$?; expected=""; }` with the clause `the COMMITS of <ref> (<sha10>) could not be counted for the credential scan (git log exited N)`, failed_creds=1.
