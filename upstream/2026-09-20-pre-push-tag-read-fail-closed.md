The class, found by execution on the text upstream landed from the fork's offer 1847: a read the hook makes of the pushed objects fails, or returns less than the objects hold, and the hook reads the result as an empty one, so a part-scanned push passes as a clean one. The eighth road, stated as executed (the round f5 entry stated it too narrowly, as gitleaks reading its git log FAILURE as an empty scan, and a fix built to that spec would still have failed open): gitleaks 8.30.1 (and 8.28.0, the version CI pins) runs `git -C <root> log -p -U0 <range> --diff-merges=first-parent` itself, and aborts its scan on the FIRST stderr line from that git that is not one it allowlists as a rename-detection warning (by execution: the two rename-detection warnings and the `diff.renameLimit` hint pass; the source names the auto-gc notice too), WHATEVER git's exit status: it logs `ERR [git] <line>` and `ERR error="stderr is not empty"`, drops the rest of the scan, reports the commits it did read as `N commits scanned`, says `no leaks found` for every finding not already emitted, and exits 0. The commit count and byte count it prints may still be the full expected ones (three commits parsed, the noise on the oldest, `3 commits scanned` equal to `git rev-list --count`, a live token in the range, `no leaks found`), so neither git's exit status nor an agreeing commit count distinguishes an aborted scan from a clean one. The hook at f5 classified on the exit status alone (`case $rc in 0) ;;`), so exit 0 read as CLEAN and the credential published, with nothing printed but gitleaks' own lines. The fix, in the fold (review round r1; the rule: stop inferring "clean" from exit 0, which says gitleaks reported no finding, not that it scanned; require positive evidence of coverage and refuse without it). The hook captures gitleaks' stderr, its log, apart from its stdout (the findings still stream live to the hook's stderr through a third descriptor: `log=$( { "$gl" git ... 2>&1 1>&3; } 3>&2 ) || rc=$?`), re-emits the log, keeps the exit-status arms (1 or above 2: failed_scan and failed_creds as before; 2: a finding), and when gitleaks CLAIMS a scan (exit 0 or 2) applies two independent conditions to an SGR-stripped copy of the log: (1) any line at its ERR level refuses, `the CREDENTIAL scan of <ref> (<sha10>) did not complete: gitleaks logged an error (<the first ERR line>)`, failed_creds=1; (2) the reported `<n> commits scanned.` must equal the hook's own count of the commits with content to scan, `covered <reported> of the <expected> commits with content to scan` on a mismatch, `reported no commit count, so what it read is unknown` when the line is absent, failed_creds=1 on each. Two conditions because either alone has a hole: the short mode writes no ERR line, and an aborted scan can report the whole count. The expected count is derived by a new helper, scannable_commits, over the SAME `git log -p -U0 --format='commit %H' --diff-merges=first-parent` stream by gitleaks' own rule (a commit counts once a file that is neither deleted nor binary has a hunk; gitleaks' sources for v8.30.1 and v8.28.0 read: one `addCommit` per fragment, a fragment one hunk of a non-deleted non-binary file, the count the distinct shas), because `git rev-list --count` over-counts every empty, delete-only, binary-only, mode-only or rename-only commit and every merge with an empty first-parent diff (nine of 22 shapes disagree with gitleaks; the derivation agrees with both gitleaks versions on all 22 and on a 4556-commit range of the fork's own history, 4544 both). The derivation's own failure is its own road, read before the scan: `expected=$(scannable_commits $range) || { rc=$?; expected=""; }` with the clause `the COMMITS of <ref> (<sha10>) could not be counted for the credential scan (git log exited N)`, failed_creds=1. The rev-list probe's comment now says what it covers (an UNRESOLVABLE range only; what gitleaks did with the range is read from its log, not its exit status), and the hook's header paragraph states the road and the two-condition remedy. The invocation's arguments are unchanged (tests/install-sh.bats pins them). Verified by execution with gitleaks 8.30.1 and 8.28.0, the hook fed its ref line directly and through REAL pushes: the noise mode is refused on both conditions (the ERR line, and `covered 0 of the 2` or `1 of the 2`: the abort's count varies with the race between gitleaks' two readers, and both refuse), the short mode by the count alone (`covered 1 of the 2`), the bad-object and fallback modes by both, the rename warning and the two-secret control still as a finding, the remote unchanged in every refusal; a clean push prints byte-identical output to the f5 text's; on a finding one INF line moves (the log is shown after the live findings). In tests/pre-push-hook.bats, the section "the credential scan's own read: gitleaks' log" (the real scanner, skipped where gitleaks is absent as tests/gitleaks-config.bats skips; the probe tokens assembled at run time; a second generic shim, `git_passing_through <bash test over "$@"> <stderr line or empty> [<appended argument>]`, keyed on gitleaks' invocation shape and no read of the hook's own, with the wrappers gitleaks_git_noisy, gitleaks_git_short and gitleaks_git_warning): the two-secret control, a clean pass with the count shown as before, the no-content shapes (an empty commit, a deletion, a binary add: four commits by rev-list, `1 commits scanned`, no hook line: a pin on the derivation rule, red on a hook that counted with rev-list), the ERR mode and the short mode (each red at the f5 text at `[ "$status" -eq 1 ]`: the fail-open), and the allowlisted rename warning as a WRN pass control.

The property in one sentence: no read the hook makes of the pushed objects, its own or the one inside gitleaks, can fail or come up short in a way the hook cannot tell from an empty result, because each read's status is captured before its output is judged, a non-zero status refuses the push as unscanned, and the one read whose status carries nothing is judged from the scanner's own log against a count the hook derives itself.
