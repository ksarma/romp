D2 of the phone reconnect plan, phone-only by the user ruling of 2026-09-18. On the phone every pane redialed at every return from the background and each took a whole connect push (feed frames, bars) on one link and one thread in the same second as the visible chat. Now a pane whose last panes word from the shell says it is off screen, on the phone layout (the shell _MOBILE_MQ probe read synchronously, the way D3 reads the link), puts its socket down for every state at a stale return (its own park(): abandon() teardown, one wsState word parked, romp:wsdown for the bundle and loader), files its return row with parked true and dials nothing (connect() guard, no awaitLink) until the shell word says its tab is on screen; the tap opens a fresh return window, re-raises the loader and dials once through D3 link rule, and the return-fresh says parked. The desktop layout and standalone pages are unchanged; a pane hidden since load still makes its first dial. The shell keeps parked as its own state so the connection cue and log stay silent. All shim lines are inserted fork-only lines; no upstream shim line is modified. Touches CLIENT_DIAG_KEYS (pane-shim gains parked, a bool approved field by field). Until K2 (kernel-side, joint with romp-performance-1) the tap costs one full frame for the opened pane only. Stacked on PR 4 (iosperf-shell-led), itself on 765 and 762. Offer waits on the user word under the no-new-upstreaming rule (2026-09-11).

Review round 1 (2026-09-18). The FEED pane is exempt from parking by the user ruling of 2026-09-18: its socket carries the card-trouble entries the shell bell mirrors (warning chips, failed follow-ups, retry storms, sync faults) and the bell surfaces trouble the user was not looking at, so a hidden feed dials on return like the visible pane through the D3 link rule, one extra redial per return accepted; keyed on the pane app alone, never on width or timing. A wid-targeted chat focus (a session tap from the feed, Sessions, Outline or the Log) aimed at a window whose chat pane is parked, or held by a dead socket, was silently dropped; it now parks in _PENDING_REVEAL on the _reveal_request road and the pane redial or ready consumes it (the sid-only slot loses the focus anchor and cite; a follow-on). park() ends the reload core fresh hold the fast path armed and tells a held reload to go; a return that passes the park branch ends an earlier park so the pane dials. The shell cue keeps the upstream wsState line byte for byte and adds one fork-only line for the parked state, so the folds see no new divergence there.

Review round 2 (2026-09-18). A jump to a REMOTE host's session (openSession, showOnTimeline, deepLink, viewReadOnly, reviveSession) posts the shell's chat reveal from the sending pane (federation.ts outbound): the remote kernel's own shell reveal reaches nobody here, and with the chat pane parked its focus parked at that kernel with nothing to un-park the pane; the pane-side reveal shows the chat pane, whose redial dials its relays and lands the parked copy (the copy is re-minted from the sid, so a remote showOnTimeline lands on the session's tail until the slot carries the message; a follow-on). _PENDING_REVEAL is keyed by window: the one slot let a session click in one window overwrite a push tap parked for another; a window's entry goes with its last client, as T347's active-chat record does. A focus copy is kept only when EVERY taker is unproven (a proven pane displayed it), and a copy tagged only with a socket the reaper dropped is retired at the reap unless the window's redialed chat pane is already connected, whose first strip lands it. _reveal_request's own unproven road keeps the any-taker shape for push taps, pre-existing and unchanged.

Review round 3 (2026-09-18). The retire at the reap never pops the park: a copy whose last unproven target the reaper dropped becomes a plain park on every path, since the reap ends the wait on a pong and not the user's gesture, which stands until a pane consumes it or the window goes away; round 2 popped the entry when no other chat client of the window was connected yet, and a keepalive beat landing between the tap and the redial it caused lost the tap on both the focus road and a push tap's boot road. The stale-replay exposure is bounded by the drop at the window's last client; a park whose reaped socket was the window's only client still goes with it through that rule, named. A remote jump posts the shell's chat reveal only when a remote socket took the op (sendTo and sendRemote report the send; a jump the relay dropped with its toast posts none, the local road's parity). REMOTE_CHAT_REVEAL_OPS is the kernel's answer set derived by AST (every arm of _dispatch_ws and _drive reaching _reveal_chat_for or _reveal_or_confirm): ten ops, the round-2 five plus createSession, pickResult, openByName, forkSession and commentPromote, the last five posting for a chat pane already forward. Kept and named, not fixed: in a split-column window whose dead-held column holds the tapped session, a proven sibling column means no copy and the tap is lost (the literal fix reopened a stale replay); a park that names no window lands on the next chat pane of any window, and a park for a wid whose page never connected a socket has no end but a consume (a sweep of the park sites dropped live taps).
