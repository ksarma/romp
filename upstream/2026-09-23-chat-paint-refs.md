An inline svg's `fill`, `stroke`, `mask`, `clip-path`, `filter` or `marker-*` attribute holding a `url()` to another origin made the browser request that document the moment a chat message or a hovered file preview rendered, with no click: the sanitizer keeps all eight attributes and nothing after it on those two surfaces read them. What left was the reader's IP address, the time, the user agent, the page's origin for `mask` (a CSS image, sent as the Referer under the kernel's same-origin policy) and whatever path and query the author wrote into the `url()`. The surfaces reached are the kernel-served dashboard and the iOS web app, not the VS Code panes, whose `img-src` names only the webview's own resources and `data:` (read from the policy's text, not executed). Red before the fix, at 6cf6839ba and with the passes removed (2026-09-23, Chromium 151): the chat witness's logger received 19 requests and the hover witness's 10. `filter`, measured by the design study as fetching only same-origin in Chromium 151 (where figure-gate.ts's 2026-09-09 note said all eight fetched), reached neither logger; on the hover path the page's request event fired for it and no request arrived. It is removed by rule. The fix is one strip (paint-refs.ts dropRemoteRefs) run inside sanitizeMd by default and in the preview card's strip; the file viewer opts out and keeps its click gate. A notice card's body on the feed page, which a session writes through POST /notice, runs both, and its witness on the kernel's own /feed page (tests/test_paint_refs_kernel_pages_browser.py) was red at 6cf6839ba: the fill, stroke, clip-path, mask and three marker references reached the logger, Sec-Fetch-Dest image and cross-site, the mask with the page's origin as Referer. A residual, disclosed and tested: the notice card (feed.ts noticeBodyNodes) calls the preview's strip with an empty base, so its paint arm now removes a relative or root-relative same-origin paint reference that sanitizeMd's own pass kept (fail closed, no request); the same empty base already cost a notice body its relative, same-origin and data: images. Passing the page's URL there fixes both and is the notice card's own follow-up; file-preview.test.ts states the current behaviour and goes red when that call changes. A `data:` paint reference stays only when its media type is a raster image (paint-refs.ts DATA_RASTER_TYPES, the type read as the Fetch standard's data: URL processor reads it): in Playwright's Firefox 153 a paint attribute naming a data: SVG, XHTML or XML document with a fragment loaded it as a resource document, and that document's own @import fetched another host as a chat message, a hover preview or a notice card rendered. With b4f9139b8's strip the chat witness's logger received the 16 @imports of a user message and a reply, and the kernel-page witness's sink 11 from a notice card and 11 from a hover preview, each Sec-Fetch-Dest style with no Referer. Chromium 151 and WebKit 26.5 loaded no such document, sanitized or not, so CI, which runs Chromium alone, holds this rule through the kernel-page witness's DOM half and the node pins (the chat witness skips in CI's npm test, as the render leg does), and the Firefox figures are the box's (ROMP_BROWSER_ENGINES). A raster data: mask stays and still draws (read as pixels in Chromium 151 and Firefox 153); the cost is that a paint attribute naming an svg, XHTML or XML data: document no longer paints on these surfaces, where Firefox was the one engine that loaded one. The file viewer drops such a document too, rather than gating it: a placeholder could name only data:, and its click would load a document that fetches hosts the label never names. Its sanitize keeps references to another origin for the gate and runs only the data: half of the pass (paint-refs.ts dropDataDocuments). With b4f9139b8's viewer, Firefox fetched the 11 @imports of a viewed file's data: documents as it opened, and the gate held a data: stroke aside with its svg's gated fill and restored it on the click, after which Firefox fetched that document's @import too. The viewer scene of tests/test_paint_refs_kernel_pages_browser.py is silent at the fix in Chromium 151, Firefox 153 and WebKit 26.5, and its DOM half runs in CI.

An .svg opened in its own tab (a Cmd, Ctrl or middle click on a path link to it in a viewed file, which opens the kernel's /file URL or the /remote/<host>/file relay's) was a document under a bare `sandbox`, which stops scripts and not loads. At 6e6ddf7d5 each tab fetched sixteen loads from the host its markup named (an image href and xlink:href, a CSS @import, a foreignObject img, a fill, a mask and a CSS fill paint reference, and nine more shapes a probe found: an feImage, a CSS cursor, a background image, an @font-face source, a stylesheet link, an image preload, a prefetch, an iframe and a video), the paint references and the font with no cookie and the rest with the browser's SameSite=None cookies for that host, none with a Referer. The kernel sends `sandbox; default-src 'none'; img-src data: blob:; style-src 'unsafe-inline'; font-src data:` as one value on every svg success (HEAD, 206, 200), the relay's included. That policy alone did not hold in every engine: in Playwright's Firefox 153 a fill, mask or filter naming a data: SVG document fetched that document's own @import from another host, and in Playwright's WebKit 26.5 a foreignObject preconnect link opened a TCP connection to its host, and no CSP directive stops either. So a navigation to an svg on /file or the relay now gets a small page that shows the file in an img (image mode), and the policy stays on the svg bytes as a second layer. An svg drawn as an image loaded nothing external in Chromium 151, Firefox 153 or WebKit 26.5, and its data: raster and inline styles still drew (tests/test_svg_tab_policy_browser.py, whose Firefox and WebKit legs run where those engines are installed). The cost: in the tab the svg's own links do not follow and its text does not select. It reduces what leaves the machine, and it reaches the user as a notice at landing.

SECURITY.md said every page's `Referrer-Policy: same-origin` keeps the token from ever reaching another origin in a Referer. After this fix one known road remains: a paint reference in a file the viewer shows, once its figure loads (its host on the gear's list, or a click on its placeholder). Executed from a bare /chat?token= page and from the shell's frame, the img and six paint references sent no Referer and the mask sent the page's origin; one run in the maintainer's fact check had recorded a chat message's fill sending a bare page's full URL with its token, which no later run reproduced. SECURITY.md and the kernel's comment now state that exception instead of the universal.
