The shim's only drop breadcrumb, the wsclose row, recorded everConnected alone, so client-diag.jsonl could not tell a declared redial (?reconnect=1) from a mid-load drop the dial term gated off, nor from a ready that reached the shim while its socket was going down. The kernel now stamps every row with the carrying socket's dial record, client["redial"], set at accept beside the consumable reconnect and never consumed, so every row a socket carries reads alike on every pane (the strip's _resolve_reconnect pops reconnect on a chat socket and nothing pops it on the other panes, so a stamp of that flag meant the opposite thing by app); and the wsclose row carries the shim's bundleReady at the close. The pair on the queued wsclose row, which rides the redial: both true, a declared redial; both false, a drop before the bundle said ready; reconnect false with bundleReady true, a ready that queued during the close and rode the redial as the page's own.

(1) The clientDiag handler block and the shim's wsclose row line are byte-identical upstream at the fold tip (459e50d6, and still at ac44ee51), so the handler hunk and the row hunk apply with offsets only; the third hunk, the accept-time comment beside the client["redial"] assignment, is the fold's text and does not apply upstream. (2) The shim half references bundleReady, which only the fork's redial-gate change declares (upstream's shim has no bundleReady: 0 hits in kernel/kernel.py there), so this offer is stacked on upstream/2026-09-10-shim-redial-gate.md and is not standalone; ported alone, the row line throws ReferenceError inside the row's try/catch and upstream stops writing every wsclose breadcrumb, silently. A kernel-only scope is not an alternative: upstream's dial term is everConnected alone, so a stamp there equals the row's existing everConnected and separates nothing. (3) The kernel half's stamp reads client["redial"], which upstream lacks (its only "redial" is a federation message type): the port adds a never-consumed accept-time copy beside client["reconnect"] = True in the same accept block (two lines), or names the field the stamp reads. With the never-consumed key the stamp is deterministic on every pane and needs no ordering argument; upstream's pusher wakes at accept and resolves every chat client with no ready filter, so a stamp of the consumable reconnect there would race the pop on the queued row. (4) The new test module's shim legs call _shim_core_js and _shim with caps=km.READY_GATE_CAP, and the new pane-shim-stale test reads the three-bit term: its gated shape, a socket that died before the bundle said ready, dials without the term, where upstream's everConnected-only term dials with it, and the file's shim extractor reads the fork's _shim(app, v=0, caps="") signature, which upstream's _shim lacks: no caps parameter at any upstream sha (def _shim(app, v=0): at the fold tips 459e50d6 and ac44ee51; def _shim(app, v=0, no_stale=False): since b1581f6c3, their #1305, the Files pane's own opt-out, and so at upstream/main 8f8d3fb1 on 2026-09-10, where the fork's is the NO_STALE_CAP cap), so the extractor's indexOf of the fork's def finds nothing there, and a ported pane-shim-stale test goes behind upstream's own extractor (the indexOf of that def, and the template tail (_reload_core(v), app, int(v), "true" if no_stale else "false", app, app)). Both exist only with the redial-gate offer, and the docs' three readings hold only with the three-bit term.
