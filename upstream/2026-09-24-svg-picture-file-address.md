The file viewer's svg picture, and a chat svg picture shown after a resumed fetch, now load from the kernel's /file address, as the composer chip, the lightbox, a notice attachment, the file hover card and a chat image's first attempt already do. The viewer keys the address on the file's mtime, so a reload shows the new picture, and reads the Content-Type's media type alone, so a charset parameter does not change the verdict. While such a picture loads, the romp loader stays beside it, in the viewer and in the chat. In the viewer a failed picture load asks the address again, once per failure: the pane then shows that answer's own words, or, when the bytes arrive and the picture fails again, a sentence naming both a failed load and bytes that will not decode. The pane that re-ask leaves comes back to the picture on the reconnect events, or on a later kernel message once the address answers. A reconnect event that arrives while the address is being asked again, or while the picture from that answer is loading, makes a failure of that attempt ask once more at once. A press of the Source toggle ends that attempt: when the person returns to the picture, a failure asks the address again once. A kernel message may send one probe of the address, three in all, and only a reconnect event, a reload, a press of the Source toggle or a picture that shows refills them; that holds in the chat page too, whose markdown-image heal leaves the viewer's picture to the viewer. A failed reload's pane does not try again by itself, as before for every file type. If the person switches to the Source view while the address is asked again, before the picture's failure, or while the file's bytes still decode, the Source view stays up, and a changed-on-disk bar whose Reload that ask took over stays usable. An svg reload that lands while those bytes decode shows its own bytes in the Source view. With the Comments panel open, its wait for a reload's bytes ends when they land or when the view shows them, whichever comes first, and its change cards update only when the view shows the new bytes. In the chat the resumed fetch keeps its progress and error words, and a picture that then fails to load drops its memo entry, so the next attempt runs the resumed fetch again, within the retry budget: the failure sets the budget's flag, which stops a fetch's progress from refilling the budget, and a reconnect event clears that flag. While the picture loads beside the swirl the swirl offers no retry, and a re-render shows the picture at once while the page holds it; before its first load, or once the page has let it go, the re-render's picture waits beside the swirl. Other image types are unchanged at both sites. The costs: an svg picture is now fetched by the image load as well (in the viewer the fetch still reads the bytes for the Source view; in the chat the managed fetch runs first, then the picture loads from /file), and in the viewer a reload replaces the old picture with the loader until the new one loads. In the chat an svg's resumed fetch no longer supplies its picture: once that fetch completes, the picture is a whole-file load of /file, and a failed picture load runs the resumed fetch again before loading the whole file again, so on a link that cuts every transfer before its end an svg that only arrives by resuming does not show. fix tier: the two pictures now load the way the surfaces named above do, and the new svg tests fail over the code before the change; the controls (a png's picture in the viewer and after a chat retry, an answer typed IMAGE/SVG+XML) and the kernel's v guards pass before and after.
