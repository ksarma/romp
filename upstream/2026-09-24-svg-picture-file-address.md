The file viewer's svg picture, and a chat svg picture shown after a resumed fetch, now load from the kernel's /file address, as the composer chip, the lightbox, a notice attachment, the file hover card and a chat image's first attempt already do. The viewer keys the address on the file's mtime, so a reload shows the new picture, and reads the Content-Type's media type alone, so a charset parameter does not change the verdict; the chat keeps the resumed fetch's progress and error words, and a picture that then fails to load takes the first attempt's failure path. Other image types are unchanged at both sites. The cost: an svg picture is now fetched by the image load as well. In the viewer the fetch still reads the bytes for the Source view; in the chat the managed fetch runs first, then the picture loads from /file. fix tier: the two pictures now load the way the surfaces named above do, and the new svg tests fail before the change, except the IMAGE/SVG+XML case, which passes before and after.
