CI's Python cells install pytest and cryptography and nothing else, so the 48 tests gated on claude_agent_sdk importing (43 in tests/test_sdk_backend.py, 5 in tests/test_host_transport.py) skip in every cell and read green having checked nothing, the two SDK-transport host tests in tests/test_session_host.py skip with them, every session host a test spawns takes the pipe transport, and 98 other tests never meet the real SDK: 25 spawned-host cases in tests/test_session_host.py whose host runs the pipe transport, and 73 in-process cases across eight other modules whose fixtures install a fake SDK only when the real module is absent (148 tests in three disjoint sets); upstream's workflow has the same shape and the same gated module. The change is one step, Install the Claude Agent SDK, between the cryptography step and pytest, reading the version from SDK_TESTED_VERSION in kernel/session_host.py with the sed bin/romp-sdk-setup runs over the same line, so the number has one declaration and the installer, the host's own version check and CI follow it; at this head that is 0.2.156, the version the box's full suite passed under (16875 passed, 566 skipped, 1 xfailed, 0 failed), while PyPI's latest was 0.2.157, released 2026-09-18 as the fifth version in four days and left alone on purpose. The step refuses an empty, malformed or duplicated constant and carries no continue-on-error: the SDK requires cryptography through mcp's pyjwt[crypto], and a lagging wheel must red the cell, not skip 48 tests. tests/test_ci_sdk_pin.py never skips: it executes the step's own read of the constant and, wherever the SDK imports, asserts the installed version equals it, so a box whose venv moved and a CI cell whose install disagreed both go red; on a venv without the SDK it checks the pin's presence and form and warns, in pytest's warnings summary, that the equality was not checked there. The bump is the constant's own act (install the new version, run the host tests, move the number); the residual is that nothing polls PyPI, a person notices a release. A second residual: the step pins the SDK alone and its dependency closure resolves fresh on every run (26 packages on 2026-09-20, the 3.12 cell of run 35518107329), so a red that no commit explains is a transitive release the pin test does not catch; one of those packages, anyio, registers a pytest plugin that every Python cell would auto-load across the whole suite, and the Run pytest step passes -p no:anyio so the cells' plugin set stays the box's (the step's comment states the decision and the measurement: the two gated modules read the same counts with and without the plugin). The 3.14t cell installs it too: on a free-threaded 3.14.6 with the GIL off the install used wheels only (cryptography, cffi, pydantic-core and rpds-py publish cp314t wheels), the import left the GIL off, and the gated pair passed (653 passed, 1 skipped, an unrelated runner-floor pin) and the host pair after the re-gates (101 passed); the SDK's classifiers stop at 3.13, so a release that breaks there shows as a red cell. Two re-gates: the two SDK-transport host tests gate on what the host's interpreter imports (a probe of sys.executable) or on the box venv, not on the venv directory, and the no-SDK control in tests/test_session_host_sdk_pin.py hides an installed SDK from its child with a sitecustomize.py blocker (under an interpreter that has the SDK it read CLINotFoundError where FileNotFoundError was expected, on 3.12 and 3.14t alike); one new control in tests/test_session_host.py hides the SDK from its host the same way and asserts the pipe transport, which otherwise has no test once the interpreter has the SDK. The Linux job cap stays at 25 minutes; its comment, which priced the cap from pytest phases of 160 to 300 s, now states the measured phases (866 to 1184 s on the run this branch was cut from, read from the Actions API) and the headroom (the Linux jobs take 16.5 to 19.9 minutes whole on main's latest run and 17.3 to 20.9 on this branch's first CI run, whose SDK step took 5.5 to 7.8 s per cell), so the cap pin in tests/test_ci_bats_bound.py is untouched; the cryptography step's comment no longer promises the 3.14t cell can continue without cryptography, which the SDK step requires. The step carries a 5 minute timeout, the file's convention for a download. Still skipping in CI: three of the four MachineVenv tests in tests/test_session_host_sdk_pin.py, which test the venv the installer builds (the fourth builds its own temp layout and runs; under CI's shape the class reads 1 passed, 3 skipped), and the two ServedRestart tests in tests/test_session_host_restart.py, which gate on the same venv directory and also need the extension bundles, so a re-gate alone would not run them in the Python job; on a plain venv without the SDK the 48 and the two host tests skip as before. Cost per Linux cell about 106.5 MB of download after the cryptography step (the SDK wheel is 102 MB there and 92 MB on macOS arm64; it bundles the Claude Code binary) and 5.5 to 7.8 s of install per cell on the branch's first CI run (5.4 to 6.8 s on this box). Travels with 2026-09-18-sdk-pin-for-private-imports (#777), which introduced SDK_TESTED_VERSION; upstream's installer installs the SDK unpinned and its tree has no such constant, so an offer there carries the step with a literal version until it does.
