run_helper ran the operator's apiKeyHelper, or a stored login's token command, through subprocess.run with a timeout, and on the timeout subprocess.run killed only the /bin/sh it had started. dash, the /bin/sh of Debian and Ubuntu, forks even a lone command, so the hung command and every process it had forked ran on after the call raised, with the helper's environment and the write end of a pipe whose read end was closed; helper_key asks again on its next call when a run fails, so a helper that kept hanging left one more each time. run_helper now starts the shell in a session of its own (start_new_session, which Python 3.10 has; process_group needs 3.11) and, when a run does not finish, sends SIGKILL to the whole process group, drains the pipe for at most HELPER_DRAIN_S (2 s) and reaps the shell, with p.kill() as the fallback: the shape kernel/kernel.py's _git_net_out already uses. On a KeyboardInterrupt, communicate may first reap a shell that has already exited, and then the group is not signalled, as before the change; on that road and every other way out of the block once it is entered, the run's own Popen context manager closes the pipe and waits to reap the shell, as subprocess.run's did (on a KeyboardInterrupt for at most the quarter second Popen allows once per run). The error words, the stdout rules and the exit 127 word are unchanged. Not covered, and pinned as stated: a process that leaves the group itself (setsid, setpgid, a daemonizing helper) runs on, and when it still holds stdout the call raises after the drain's 2 s. The session also takes the controlling terminal away from the helper, so one that prompts on /dev/tty fails at once where a kernel started in a terminal let it prompt, and a terminal's Ctrl-C no longer reaches it. The manager's kernel restart signals the kernel's pid alone, so a hung helper runs on through it, before the change and after it alike; under the systemd unit, KillMode=control-group ends it only at a unit stop or restart. The cleanup of the kernel's process group at an exit no longer reaches a helper running at that moment, because its session is its own: a terminal's Ctrl-C, or the SIGHUP when the terminal closes, for a kernel started in a terminal, and, under the macOS launchd agent (whose plist sets no AbandonProcessGroup), launchd's kill of the job's process group when the manager's job ends. Before the change each of those reached such a helper; now it runs on until it exits on its own, and this change does not end live helper groups at an exit. It changes a kernel credential path, so the fork lands it only on the owner's word, and offering it upstream is his call.

upstream/main (fetched 2026-10-06) carries the same run_helper, its text identical to the fork's before this change, the same three callers (helper_key, and logins.token_value from kernel/sdk_backend.py and kernel/judge.py) and the same test_a_timeout_is_a_static_word_too. Its kernel/credentials.py, given a hung command whose shell forks a child that forks a sleep and a 1 s bound, left the child and the sleep running after the call raised.
