upstream/main's docs/architecture.md carries the clause their PR https://github.com/romp-on/romp/pull/1295 (20346b22, merged 2026-09-10, written from this fork's round-1 text) put there: the venv is rebuilt by bin/romp-sdk-setup when you move romp to another Python by setting ROMP_PYTHON, when the interpreter it was built with is gone and no other of its version and build remains, or when an interrupted build left it without pip; and the kernel runs ROMP_PYTHON if set, else the interpreter the venv's pyvenv.cfg records. Two of the three cases and the kernel rule are not the script's. The pip gate (bin/romp-sdk-setup:216-220) fires whenever the venv's own bin/python or bin/pip is missing, and bin/python is a symlink to the recorded interpreter, so removing it rebuilds the venv whether or not another Python of the same tag remains (tests/install-optional-deps.bats:349: pick_python takes the other python and says the venv still matches, and the gate rebuilds anyway). The newest-first case (the tag compare at :208-214) fires when the recorded interpreter no longer runs as its version and build, gone or repointed, and no other Python of that version and build is on PATH or in ~/.local/bin. The kernel's rule has a third branch: another Python of the venv's version and build when the recorded one is gone or no longer runs as that version and build. This PR's clause states the three cases and the same-tag branch exactly; the offer re-syncs upstream's clause to this text, cut from upstream/main at or after 20346b22. The fold of 20346b22 conflicts with this PR's docs/architecture.md hunk, and this PR's clause is the resolution; the ruling rests on the script (round 2's correctness finding), not on a pin, since the architecture pin passes on upstream's clause too. The same PR adds one clause to docs/reference.md's move paragraph (upstream's text, byte-identical to the fork's before it): after bin/romp-sdk-setup, a machine with the Codex backend set up re-runs bin/romp-codex-setup, which follows the SDK venv's record and rebuilds codexvenv for the new interpreter; nothing on the restart path runs it, and the kernel refuses Codex sessions until it does. The fork's install.md section is not part of this: their #1282 wrote upstream's own from the fork's offer branch, and the fork's section, which carries upstream's hazard sentence, survives the fold.
