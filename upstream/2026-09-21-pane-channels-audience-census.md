Upstream's PANE_CHANNELS in ui/webview/federation.ts (from PR 1839) is a hand-kept set of the four panes that render a pushed channel a remote host can be heard on, and ui/webview/federation-reconnect.test.ts drives the panes it names one at a time (the feed and the timeline on their own channels, the chat on the tab list, settings and files pending nothing), so nothing there reads the kernel's push audiences: a pane the kernel pushes to that the set misses pends no host and posts nothing to the shell, which is how this fork's fifth pushed-channel pane, the Waiting-on-you pane (app `waiting`, in the feed branch of kernel.py `_push` beside the feed pane and the Outline), dropped out of the pending signal at the fold that brought the set in. The fork's census case reads kernel/kernel.py's `_push` body and matches every `c["app"] in (...)` tuple and every `c["app"] == "..."` singleton (the feed branch and its twin in the except arm, the warm gate's pair, the chat's and the timeline's singletons), asserts that the union of those apps equals PANE_CHANNELS in both directions (an app `_push` addresses that the set misses; a set member `_push` never addresses, which would pend every attached host forever), and drives each member through the manager on the channel its audience names (a tuple naming feed places its members on the feed payload, one naming chat on the tab list, one naming timeline on the lanes, a singleton on its own name), asserting that the other two channels' frames retire nothing and that its own channel's first frame retires it; the offer's only change to federation.ts is the `export` on PANE_CHANNELS, which the census imports. The fork-only member, `waiting`, stays in the fork's set and is no part of the offer, nor is the census's clause asserting that the union carries `waiting`, nor the fork's Waiting-on-you case above it; upstream's copy of the census reads upstream's own `_push`, whose tuples and singletons at the fold's pin name exactly the four apps of upstream's set (the feed pane and the Outline in the feed tuples, the chat and the timeline by singletons), so the equality holds there as it does here (the census with its `waiting` clause dropped, run against upstream's kernel at the fold's pin and its four-name set in a scratch copy: green). The census yields two reds by construction, each shown in a scratch copy of this tree: widening an audience with a name the set misses (the timeline's singleton made a tuple carrying a second app) fails the first direction naming that app, and adding that name to the set as well fails its drive, because `pendingFor`'s selector falls every app that is not the timeline or the chat to the per-host feed, so the host's feed frame retires a member whose audience names the lanes. The offer, the census case with the export and nothing else, waits on the offers pipeline.
