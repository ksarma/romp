Upstream's PANE_CHANNELS in ui/webview/federation.ts (from PR 1839) is a hand-kept set of the four panes that render a pushed channel a remote host can be heard on, and ui/webview/federation-reconnect.test.ts drives the panes it names one at a time (the feed and the timeline on their own channels, the chat on the tab list, settings and files pending nothing), so nothing there reads the kernel's push audiences: a pane the kernel pushes to that the set misses pends no host and posts nothing to the shell, which is how this fork's fifth pushed-channel pane, the Waiting-on-you pane (app `waiting`, in the feed branch of kernel.py `_push` beside the feed pane and the Outline), dropped out of the pending signal at the fold that brought the set in. The fork's census case reads kernel/kernel.py's `_push` body and accounts for every read of the `app` key in it, whatever expression reads the key, against three forms it can read (the body first normalised: comments dropped, a backslash continuation joined, a newline inside brackets folded, so a wrapped tuple reads as one line): a tuple of string literals, however wrapped or spaced and with members of any name (the feed branch and its twin in the except arm, the warm gate's pair), a singleton compared by `==` with a string literal of any name (the chat's and the timeline's, the Outline's through `c.get`), and a value formatted into text (the send log line's `%` operand), which is no audience; every other form (a membership test against a name, an attribute or a call, such as a named constant; a membership test against a list or a set literal; a tuple with a member that is not a string literal; a negated test; an equality test against anything but a string literal; a `.get` with a default; the read bound to a name; a read in any other position, a call's argument or a returned value) is named, counted over the body and asserted absent, so a pane added to any of `_push`'s audiences in any spelling reads red, in the roster or as a named form with its statement and line (review round 3, 2026-09-21: a wider regex was defeated by a named constant, which no pattern over literals can read; the enumeration turns that red). It then asserts that the union of the read apps equals PANE_CHANNELS in both directions (an app `_push` addresses that the set misses; a set member `_push` never addresses, which would pend every attached host forever), and drives each member through the manager on the channel its audience names (a tuple naming feed places its members on the feed payload, one naming chat on the tab list, one naming timeline on the lanes, a singleton on its own name), asserting that the other two channels' frames retire nothing and that its own channel's first frame retires it. A second case plants a synthetic `_push` carrying every named form and every relaxed spelling (a tuple wrapped over three lines with a comment inside it, a hyphen and a digit in a member's name, a trailing comma, an unspaced pair, a backslash continuation, a `%` operand, an f-string field, a docstring naming the key) and asserts that each detector fires exactly where planted, that the roster reads the relaxed spellings, that the formatted values read as text, and that every read lands in exactly one form. The census reads `_push`'s body, the pusher's send loop, and no more: senders outside it test the app key themselves (`_feed_first`'s cold first feed frame, `_send_feed_now`'s ready-time frame, the tab strips of `_push_session_now` and `_confirm_close_now`), each addressing a pane `_push` also addresses today, and none is read, so a pane pushed only by a route outside `_push`'s body is outside the census's claim; the test's title and federation.ts's PANE_CHANNELS comment state the same scope. A pane the set misses posts no `hostsPending` at all (round 3's refuters measured this): `pendingFor` returns an empty list for an app outside the set, so the shell loses its connected-loading caveat for that pane while the pane's own loading line still shows, the direction of the Waiting-on-you dropout; the forever-pending direction is the other miss, a set member `_push` never addresses, which the equality's second direction catches. The offer's only change to federation.ts is the `export` on PANE_CHANNELS, which the census imports. The fork-only member, `waiting`, stays in the fork's set and is no part of the offer, nor is the census's clause asserting that the union carries `waiting`, nor the fork's Waiting-on-you case above it; upstream's copy of the census reads upstream's own `_push`, whose reads of the app key at the fold's pin all take the three readable forms (the feed pane and the Outline in the feed tuples, the chat, the Outline and the timeline by singletons, the send log line's formatted value) and name exactly the four apps of upstream's set, so no named form fires and the equality holds there as it does here (the census and the premise case with the `waiting` clause dropped, run against upstream's kernel at the fold's pin and its four-name set in a scratch copy: green). The census yields reds by construction, each shown in a scratch copy of this tree: widening an audience with a name the set misses (the timeline's singleton made a tuple carrying a second app, a wrapped tuple gaining a member, a hyphenated name in a one-line tuple) fails the first direction naming that app; an audience rewritten as a named constant fails the premise assertion naming the form, the statement and its line; adding the new name to the set as well fails its drive, because `pendingFor`'s selector falls every app that is not the timeline or the chat to the per-host feed, so the host's feed frame retires a member whose audience names the lanes; a compliant rewrap of an audience with no new member stays green. The offer, the census case with its normaliser, its classifier and the named forms, the premise case and the export, and nothing else, waits on the offers pipeline.
