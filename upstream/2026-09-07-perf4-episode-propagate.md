Two judge-pass costs the 120 s steady profile of the live kernel put on the serial producer segment and the triage thread. The boundary check guarded one early return with two pure predicates in the wrong order for cost: `resume_lineage` (read and json.loads every row of states/<sid>.jsonl, unmemoized) before `episode_rows` (an mtime memo, one stat on a hit); at steady state every head is recorded, so every pass parsed every states file to reach a return the stat gives. Swapped, with the fork-versus-clear decision unchanged (the lineage is still consulted before any append). `run_propagate` took a plain `load_goals` for every discovered session every pass to decide, for every live ref, not to write; the reads now go through the shared read-only cache the pusher keeps warm, and a writer object is loaded only when the view says a tracker is open under a complete recipient goal or has a reply, with the predicate re-derived on the writer's node so a completion published between the two reads is not recorded twice; the absent-store memo evaluates a view an earlier ref took under the identity taken before that read. Measured on the sealed 31-session state copy with the judge paused, two back-to-back pairs: `run_propagate` idle 0.150/0.156 s to 0.012/0.013 s CPU per pass, 37 plain loads to 0 (37 shared reads); the boundary tick 0.060/0.059 s to 0.002 s per tick, 31 `resume_lineage` calls to 0; the whole idle triage sequence 99 to 61-64 plain loads per pass. `/perf goals.lineage_reads` counts the remaining reads. The `_fileset_key` fix is a robustness find from the round-4 test sweeps: a str leaf beside Path entries in the frame's key set made `sorted()` raise TypeError, which `_frame_parse_key` does not catch, aborting the pass for that session.
