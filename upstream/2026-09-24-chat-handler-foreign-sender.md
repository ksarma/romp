windowSender classifies a message event by its source and origin (self, embedder, dispatch, peer, foreign), and the chat handler returns before any arm when the class is foreign. Every class that posts to the chat today is still heard: the shell's split-column adopt and relays (embedder), the file viewer mounted in the chat (self), a second chat column's forwarded frames (peer), the kernel's frames through the pane shim and federation.js (dispatch: no source and no origin), and the VS Code webview host (peer). A message with no source that carries an origin is not dispatch: a frame removed right after it posts can leave its message sourceless in Chromium, so the helper judges such a message by its origin alone (this origin is a peer, any other is foreign). VS Code's script in the webview's frame sets window.parent to the frame itself from release 1.103 on and deletes it in 1.88 to 1.102, so the host that forwards the extension's messages is never the frame's parent; it posts from its own window on the webview's origin. That comes from reading VS Code's webview host page at those release tags and from a browser probe of its frame structure in chromium, firefox and webkit, not from running VS Code. No arm VS Code delivers to may be narrowed to self and embedder. Upstream's chat handler has the same head with no sender check, so the change applies there as it is. The helper and window-sender.test.ts are byte-identical to the copies in the patch prepared for upstream PR 2113, which adds the same return to that PR's chat handler, so a later fold of that PR merges them without conflict. chat-foreign-frame.test.ts is the fork's own: that patch's copy describes and exercises arms of PR 2113's chat handler the fork does not have, so a fold takes that patch's copy of the file. fix tier: chat-foreign-frame.test.ts fails before the change (a foreign adopt, editorSelection and session frame each reach their effect, a sourceless one with an opaque origin included) and passes after it.
