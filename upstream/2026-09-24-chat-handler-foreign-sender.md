windowSender classifies a message event by its source and origin (self, embedder, dispatch, peer, foreign), and the chat handler returns before any arm when the class is foreign. Every class that posts to the chat today is still heard: the shell's split-column adopt and relays (embedder), the file viewer mounted in the chat (self), a second chat column's forwarded frames (peer), the kernel's frames through the pane shim and federation.js (dispatch, no source), and the VS Code webview host (peer). VS Code's script in the webview's frame sets window.parent to the frame itself from release 1.103 on and deletes it in 1.88 to 1.102, so the host that forwards the extension's messages is never the frame's parent; it posts from its own window on the webview's origin. That comes from reading VS Code's webview host page at those release tags and from a browser probe of its frame structure in chromium, firefox and webkit, not from running VS Code. No arm VS Code delivers to may be narrowed to self and embedder. Upstream's chat handler has the same head with no sender check, so the change applies there as it is. The helper and both test files are byte-identical to the ones in the patch prepared for upstream PR 2113, which adds the same return plus self-only checks on that PR's viewer arms, so a later fold of that PR merges them without conflict. fix tier: chat-foreign-frame.test.ts fails before the change (a foreign adopt, editorSelection and session frame each reach their effect) and passes after it.
