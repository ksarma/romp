windowSender classifies a message event by its source and origin (self, embedder, dispatch, peer, foreign), and the chat handler returns before any arm when the class is foreign. Every class that posts to the chat today is still heard: the shell's split-column adopt and relays (embedder), the file viewer mounted in the chat (self), a second chat column's forwarded frames (peer), the kernel's frames through the pane shim and federation.js (dispatch: no source and no origin), and the VS Code webview host (peer). A message with no source that carries an origin is not dispatch: a frame removed right after it posts can leave its message sourceless in Chromium, so the helper judges such a message by its origin alone (this origin is a peer, any other is foreign). VS Code's script in the webview's frame sets window.parent to the frame itself from release 1.103 on and deletes it in 1.88 to 1.102, so the host that forwards the extension's messages is never the frame's parent; it posts from its own window on the webview's origin. That comes from reading VS Code's webview host page at those release tags and from a browser probe of its frame structure in chromium, firefox and webkit, not from running VS Code. No arm VS Code delivers to may be narrowed to self and embedder. Upstream's chat handler has the same head with no sender check, so the change applies there as it is. The helper is byte-identical to the copy in the patch prepared for upstream PR 2113, which adds the same return to that PR's chat handler, so a later fold of that PR merges it without conflict. window-sender.test.ts is that patch's copy plus four tests the fork added after it: origins whose text overlaps this document's origin (another port whose text begins with it, the origin without its port, the same host and port on another scheme), a window with no location, a call with no window argument, which is how render.ts calls the helper, and windows related to this one other than as its parent (a frame inside it, a window it opened, the window that opened it, its parent's parent), each judged by its origin. The added lines apply to that patch's copy unchanged; until that copy has them, a fold keeps the fork's copy of the file. chat-foreign-frame.test.ts is the fork's own: that patch's copy describes and exercises arms of PR 2113's chat handler the fork does not have, so a fold takes that patch's copy of the file. fix tier: chat-foreign-frame.test.ts fails before the change (a foreign adopt, editorSelection and session frame each reach their effect, a sourceless one with an opaque origin included) and passes after it.

The same check now fronts every other window message listener in the webview bundles. listenForFrames (frame-listener.ts), the one window install the feed, Outline, Waiting on you, chat and VS Code timeline frame handlers share, hands its handler no message from a foreign sender; the chat keeps its own head check, which is redundant now and stays so a fold of the PR 2113 patch stays clean. The federation registry path is unchanged: only federation.js calls it, with a MessageEvent it built itself. Each other listener returns first on a foreign sender, before any arm: the Waiting pane's panes cache, installSettingsSync (the VS Code settings sync), the shared file viewer (initFileView), the file browser (initFileBrowse), the file-comments panel's replies (ensureListener), the gear's six (taskTracking, browseResult, settingStale, models, openSettings, logUnseen), the shell palette's two (openKeys, hotkeyConfigure) and the VS Code strip's. Each hears every class but foreign, which covers its real senders: the kernel's replies dispatched in the document or forwarded by the VS Code webview host, the shell (a pane's embedder; to the shell's own page its panes are windows on its origin) and the document itself. No listener is narrowed below that, since every listener VS Code delivers to hears the host as a window on the webview's origin. foreign-sender-listeners.test.ts runs each listener, four as installed (listenForFrames, installSettingsSync, initFileView, initFileBrowse, over a stand-in global window) and the rest lifted out of their files by the TypeScript parser and run over stubs, from seven foreign senders and nine heard ones; and it takes a census of every addEventListener("message", ...) call in ui/ (tests excluded): each must open with the check, preceded by nothing but reads of the message, and must be one of the gated sites with an executed leg; a second census holds that in every ui/ file that calls the check, the name windowSender is bound once, to the helper's own import (gear.js: its require), and never written. At upstream's f4a572008, frame-listener.ts, settings.ts, file-view.ts, file-browse.ts, gear.js and strip.ts carry the same listeners with no sender check, so those hunks apply there as they are; waiting.ts and file-comments.ts are fork files. Upstream's palette-main.ts already checks both of its listeners, on the same lines, with paneSourceOk (ui/webview/pane-source.ts, which reads the shell's window.__rompPaneSourceOk and fails closed; it admits only a same-origin child iframe of the shell not marked data-protocol=none), so a fold of upstream's pane registry resolves those two lines to upstream's. fix tier: foreign-sender-listeners.test.ts fails before the change (each listener's foreign leg, 15 of them, and the census) and passes after it; with any one check removed, only that listener's foreign leg and the census fail.
