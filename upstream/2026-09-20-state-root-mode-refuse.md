kernel/judge.py makes the state root 0700 at import, best-effort, swallowing the OSError, and since 2026-09-19 reads the mode back and says one stderr sentence when it is not 0700, refusing nothing. So a root this uid does not own stays loose with one line nobody reads, a root loosened after boot is never read again, and the premise of _atomic_write's interim-mode argument (a file written at a looser mode is not exposed because the root is owner-only) rested on a diagnostic. The check now has a consequence, and after round 2 the consequence is ONE shape: the process exits with code 2. A root with a group or other write bit (mode & 0o022) is the cross-session code-execution road (another local user can plant or replace entries under it); a root whose mode cannot be read is unverified (a stat on a local directory does not fail transiently, so an unreadable root was removed, renamed or made untraversable, and continuing would re-create it under a parent someone else may own). Either verdict exits.

The exit is the round-2 decision (the 2026-09-20 review's section A). Round 1 answered a runtime refusal with a 503 latch that closed the kernel's two doors (the HTTP handler and the WebSocket read loop) and left every internal writer running under the hostile root, the housekeeping pass whose own first stage had set the latch included, so the write primitive the code-execution road depends on carried on for the life of the latch. An exit is the only shape that stops every writer by construction: the housekeeping pass, the pusher, the judge passes, the timers, the SDK backend's threads. So the latch, its 503 body, the WebSocket refusal frame and refusingSince are gone.

The refusal fires at three places. FIRST at the kernel's module import (_state_root_import_gate), right after the judge module loads and before TOKEN = _load_token() reads the serve token and _persist_repo_root() writes under the root, so the kernel never adopts an entry a writable root already held; the remedy says entries planted while the root was writable are not to be trusted (remove serve-token and repo-root, then chmod 700 the root). This closes the ordering hole (fresh-2): before it, the boot check ran only in main(), after the import had already read or minted the token, and a planted symlink at serve-token killed the import with the token's RuntimeError so the state-root refusal never printed. The verdict stands on the mode as READ AT THAT CHECK, which for the import gate is after the judge module's own repair chmod (the settled rule, round 2b): a pre-existing root this uid owns that read 0777 before that chmod and reads 0700 at the gate is NOT refused, since the same rule would refuse the first boot after every creation of the root by another tool under a group-writable umask (bin/romp-manager's mkdirSync, `romp engine`'s mkdir -p and every test harness's makedirs make the root at the umask's mode, 0775 under 002, and the judge module's import is what tightens it), and the ruling's arm ONE is stated on the current mode. What the import read is REPORTED at boot instead, loud and not fatal: the judge module records the mode it read before its chmod (_STATE_ROOT_MODE_AT_IMPORT) and whether its own mkdir created the root (_STATE_ROOT_CREATED_AT_IMPORT: the mkdir runs without exist_ok), and the boot files one stderr line and one error-centre row for a PRE-EXISTING root that read anything but 0700 and was tightened (_state_root_import_mode_row), with the distrust remedy when the read carried a write bit: entries planted while it was writable are not to be trusted, so remove serve-token and repo-root under the root and restart, and the next boot re-mints them. A root the import CREATED is exempt from the report: a fresh directory carries the umask's mode until the chmod that follows, a creation default and not a loosening. The adoption risk of a root that was writable before this process tightened it is closed by the serve-token loader (it reads or tightens no token through a symlink and faults on a foreign-owned or unchmodable one, its own RuntimeError and exit 1) and by repo-root's atomic replace below; the import gate itself refuses a root whose chmod could not tighten it (it still reads writable) and one whose mode cannot be read. repo-root is written by a temp and os.replace, the token mint's shape (fresh-1's second half): a planted entry at the path, a foreign-owned file write_text could not overwrite or a symlink it wrote through, is replaced, and a write that fails is said on stderr with its errno and filed as an error-centre row at boot (_REPO_ROOT_WRITE_ERROR, _repo_root_write_row) rather than swallowed. SECOND at boot in main(), before any thread starts (SystemExit(2) in the main thread, on the mode as read there), which is where the warn surface lives and where the import's own pre-chmod mode, when it differed on a pre-existing root, is reported as a warn-class transition (loud, not fatal: "read 0755 at import, re-tightened to 0700", or "read 0775 at import (writable by other local users), re-tightened to 0700" with the distrust remedy). THIRD on a cadence while serving: the housekeeping pass re-reads the mode as its first job and every HTTP request re-reads it before routing, each read standing for at most STATE_ROOT_CHECK_S seconds (15; ROMP_STATE_ROOT_CHECK_S overrides). A refuse or unknown verdict found there calls os._exit(2) from whichever thread found it (_state_root_exit_now: the full line with the path to stderr, a flush, no drain and no further write), idempotent under a flag; a second finder raises _StateRootExiting and never returns a verdict to its caller, so no request or stage runs on under the hostile root while the first finder's line is in flight. os._exit, not SystemExit, because SystemExit raised from a non-main thread is swallowed by the thread bootstrap and would kill that thread alone. The manager sees exit 2 and restarts; the import check refuses again while the root reads so, so the manager crash-loops one line per attempt into its log until the root is repaired, and a deploy parked on the quiet window applies into a kernel that refuses at its next boot the same way (the /busy poll misses and the parked apply lands on a kernel that will not stay up).

The re-check READS the mode before it REPAIRS (the 2026-09-20 review's extra6-1). The verdict is taken from the mode as read; the best-effort chmod 0700 runs after and is reported (repaired, modeAfter), so a root this uid owns that was loosened after boot is re-tightened AND leaves a trace, rather than the silent re-tighten round 1 shipped. The import records the mode it read before its own chmod (_STATE_ROOT_MODE_AT_IMPORT) and which call failed (_STATE_ROOT_REPAIR_STEP: mkdir or chmod, so a mkdir failure is not mislabelled as a chmod's) with its errno; state_root_mode_check folds the import's failed call into err when it checks its own root, labelled as the import's (correctness-3). A root that is not 0700 but not writable by others (0750, 0755, 0711) is a privacy fault, not a code-execution one: one error-centre row per transition and one stderr line, no exit. The rows ride _sync_notice under the bell's "refused" kind (not the mutable "sdk" kind of _sdk_problem, whose one mute would hide a security row with a Claude-backend error; extra7-1), are keyed on the verdict AND its cause so an errno that changes under a constant mode refiles (extra6-2), and are built to fit SYNC_NOTICE_FIT whole with the point and the remedy first and the root's path named at most once (extra7-2); the full line with the path goes to stderr. _sdk_problem's seq collision (seq = len(ring)+1 over a ring trimmed to 20, so a long-lived kernel's rows share one signature and the bell's seen-set drops them) is pre-existing and not fixed here; disclosed because these rows no longer ride _sdk_problem.

A failed mkdir or chmod is recorded as "ENAME: strerror" (errno.errorcode and os.strerror, never the exception's text, which carries the path) and reaches the same line, row and /version field, a root that reads 0700 but whose chmod this uid cannot run included (verdict ok with a line, one row per transition). /version carries stateRootMode (verdict, modeRead, modeAfter, repaired, err, importRepairError, remedy, checkedAt) with no filesystem path (the route answers with no token, and the root's default sits under $HOME): the approved deviation, still standing. A served kernel only ever shows verdict ok or warn there, since refuse and unknown exit the process. The check reads the mode of the path the root resolves to and nothing else (not the parents, the owner, or whether it is a directory).
