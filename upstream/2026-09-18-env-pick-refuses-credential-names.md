The per-session env pick (romp new --env, POST /new, SdkBackend.spawn and set_env) lands in the session registry and the per-sid sdk-flag-settings/<sid>.json file, and its door (env_request_error, mirrored by the kernel's _env_error) refused only the three login names, so a credential-shaped variable of any other spelling typed into the pick (a NOTES_API_TOKEN, an OP_* name) was written to disk (found by the spawn.json fix's build, 2026-09-18), against the fork's rule that no credential is ever written to a file. Every door now refuses a pick carrying any name the spawn.json writer moves (spawn_env_secret_names over the pick itself: a non-empty value under a name ending _API_KEY or _TOKEN, or one of 1Password's, in any letter case for both halves since review round 1), with one rule and one wording held in credentials.py for both copies of the validator; the message names the variables, never a value, says the pick was not saved and where such a value belongs by the half of the rule it matched (a 1Password name is not sent to the process environment, which the boot check refuses), and each door adds its "env: " head once. The control token's exclusion is the boot notice's alone (round 1), so the doors, the writer and the reference's lister agree on ROMP_SERVE_TOKEN too. Nothing is written when refused and the stored env stands; set_env logs its refusal as a problem row, the /new echo and `romp new` carry a backend refusal as envRefused rather than printing the pick as applied, and the parked-op drain reads set_env's verdict and answers the chat with a names-only refusal. A stored env from before the rule still launches whole and is named once per session in the problem ring as a fact (the session launches with it; its value is in the registry and the flag-settings file), with no remedy promised: this change removes no value already stored, and a re-declaration does what it did before the door (the registry follows it at once, the file at the next connect that writes it). A fork copies no such name from its parent's stored env, on its own names-only line, so a cut turn or a comment thread mints no file carrying the value. The one writer of the flag-settings file refuses a sid that is not a bare file name and a path that is a symbolic link before touching anything, and writes on write_reg's pattern (a writer-unique temp renamed into place, unlinked in a finally), so its bytes never go through an existing inode (a hard link keeps the old file's bytes, as a copy would, and is never refreshed) and a launch never reads a torn file. Every problem row about a per-session env or its file has an error-centre form whose length is a function of its format (one variable named and the rest counted, the session name or sid and the named variable cut to a budget each, an error's class name cut to a budget), with the worst case computed from the format in the tests, and the kernel log line keeps every name whole. The reference documents the refusal, where the value belongs, the stored-env fact, the fork, and a names-only lister over the two launch files and the temp files a killed kernel can leave beside them, spelling the doors' own rule and resolving the state root the way romp does; the lister is pinned by execution against credential_env_names. Review round 3 (2026-09-19) split the redaction road (a re-declaration that removes a stored value from every file) out of this change: seven roads across three rounds by which it reported success while the value stayed on disk, three mutable stores with no single authority; that road waits on a design note. Tests: the door by name and never value, the lockstep table, the op-name fold by intent, the backend end to end (a refused pick writes nothing, the value in no file under the state root after a refused pick or a fork), the /new HTTP door, the drain's env arm, the (took, parked) verdict, every row's worst case from its format, a plain name still landing. The kernel side goes live at the next kernel restart; an offer waits on the user's word.
