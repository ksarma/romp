The per-session env pick (romp new --env, POST /new, SdkBackend.spawn and set_env) lands in the session registry and the per-sid sdk-flag-settings/<sid>.json file, and its door (env_request_error, mirrored by the kernel's _env_error) refused only the three login names, so a credential-shaped variable of any other spelling typed into the pick (a NOTES_API_TOKEN, an OP_* name) was written to disk (found by the spawn.json fix's build, 2026-09-18), against the fork's rule that no credential is ever written to a file. Every door now refuses a pick carrying any name the spawn.json writer moves (spawn_env_secret_names over the pick itself: a non-empty value under a name ending _API_KEY or _TOKEN, or one of 1Password's, in any letter case for both halves since review round 1), with one rule and one wording held in credentials.py for both copies of the validator; the message names the variables, never a value, says the pick was not saved and where such a value belongs by the half of the rule it matched (a 1Password name is not sent to the process environment, which the boot check refuses), and each door adds its "env: " head once. The control token's exclusion is the boot notice's alone (round 1), so the doors, the writer and the reference's lister agree on ROMP_SERVE_TOKEN too. Nothing is written when refused and the stored env stands; set_env logs its refusal as a problem row, the /new echo and `romp new` carry a backend refusal as envRefused rather than printing the pick as applied, and the parked-op drain reads set_env's verdict and answers the chat with a generic refusal that names nothing of the pick (the pick's names reach the kernel's stderr line alone, through the parked chip's renderer). A stored env from before the rule still launches whole and is named once per session in the problem ring as a fact (the session launches with it; its value is in the registry and the flag-settings file), with no remedy promised: this change removes no value already stored, and a re-declaration does what it did before the door (the registry follows it at once, the file at the next connect that writes it). A fork copies no such name from its parent's stored env, on its own names-only line, so a cut turn or a comment thread mints no file carrying the value. The one writer of the flag-settings file refuses a sid that is not a bare file name and a path that is a symbolic link before touching anything, and writes on write_reg's pattern (a writer-unique temp renamed into place, unlinked in a finally), so its bytes never go through an existing inode (a hard link keeps the old file's bytes, as a copy would, and is never refreshed) and a launch never reads a torn file.
