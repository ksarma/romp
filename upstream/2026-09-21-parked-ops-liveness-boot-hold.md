tests/test_kernel_parked_ops_liveness.py now releases the kernel's boot judge hold in setUp (km._wait_boot_attached = lambda: True, the idiom of tests/test_judges_process.py) and ends the real km._producer it starts on every exit path: the producer's end (the stop seam, the gate, a bounded join), the pass's stubs and the T282 census are cleanups registered before the start and run LIFO after tearDown, and an executed leak case runs both stop shapes as nested cases. The new tests/test_thread_stop_census.py derives, by AST over tests/*.py, every thread a test starts, its kind (loop, waits, bounded) and how its stop is reached, and holds that no loop or waiting thread has its stop behind an assertion; the four other sites it named are fixed the same way. Why: kernel 3421c94d0 (2026-09-11, upstream-authored) put an 8 s boot hold (BOOT_JUDGE_HOLD_S, _wait_boot_attached) in front of the producer's first pass, and this test (2026-09-03) polls 5 s for that pass, so alone it failed on "a judge pass is in flight" (1 failed, 1 error in 10.9 s). The module passed serially only because its alphabetically first test's _pusher_cycle() reaches _sdk() and builds an SdkBackend whose boot reconcile fires attachDone as a side effect; under xdist the target landed in a worker with no module-mate ahead of it and was red in every full sweep since 2026-09-11 (never in serial CI). The failed assertion skipped the stop on the body's tail and tearDown only cleared the flag, so an unpatched judge loop ran for the rest of the worker's life; the T282 census named it and could not stop it. Upstream carries the same test and the same hold; this fix was NOT run upstream (unverified there).

The blast radius, proven by romp-manager's probe (2026-09-21): the leaked loop runs _compact_goal_stores() on its 3 s backstop, globbing jd.GOALDIR and rewriting any store whose mtime moved; km.jd is the one process-wide sys.modules["romp_judge"], and later modules jd._rebind_state() it onto their own roots, so the leaked loop archives stores it never owned (a store saved under a private sid with a cleared root was archived 7.5 s later by the leaked thread); 13 modules save stores with cleared roots and 18 assert on the archive, so the leak can produce a spurious pass as well as a spurious failure in a module that did nothing wrong. Not determined, carried: whether the leaked loop produced flakes in earlier sweeps. The SdkBackend side-effect build is benign on its own (its orphan reap is gated on its own empty registry; sweep_dead_test_roots removes only romp-tests-* roots whose marker names a dead pid).

Measured in a hermetic scope with a 17-byte TMPDIR: the target alone 1 failed, 1 error in 10.94 s before, 1 passed in 0.20 s after; the module serially 9 passed in 0.28 s before, 10 passed in 0.80 s after; the module under -n 2 --dist load 10 passed; the leak case alone 1 passed in 0.71 s; tests/test_thread_stop_census.py 19 passed in 23 s (948 modules read, 395 start rows: 180 loop, 22 waits, 193 bounded; 0 tail-only among the pinned kinds, 0 unreadable receivers; 15 planted shapes); tests/test_judges_process.py with the three other changed modules 82 passed. The full sweep at the head is recorded in the fork's notes (parked-ops-notes).

Tier: fix on the user's word (a test red in every full sweep for ten days, and a leaked kernel loop with a blast radius across modules); the change is inside tests/ only. Upstream (romp-on/romp main 31b87e45f) carries the same test and hold; the fix was NOT run there.
