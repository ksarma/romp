tests/test_kernel_parked_ops_liveness.py now releases the kernel's boot judge hold in setUp (the stub tests/test_judges_process.py uses, a lambda returning True, here as one of setUp's patchers so tearDown restores it) and ends the real km._producer it starts on every exit path: the producer's end (the stop seam, the gate, a bounded join), the pass's stubs and the T282 census are cleanups registered before the start and run LIFO after tearDown, and an executed leak case runs both stop shapes as nested cases. The new tests/test_thread_stop_census.py derives, by AST over tests/*.py, every thread a test starts, its kind (loop, waits, bounded) and how its stop is reached, and holds that no loop or waiting thread has its stop behind an assertion; the other sites it named, in three more files, are fixed the same way, one commit per file, and the three the second pass's stricter reading named (AttachStandDown's lease beater in tests/test_host_transport.py, the live-tail hammer's session thread in tests/test_sdk_stream_survives_handler_errors.py, the byte-exact drain in tests/test_ws_send_bounded.py) likewise, one commit per file. Why: kernel 3421c94d0 (2026-09-11, upstream-authored) put an 8 s boot hold (BOOT_JUDGE_HOLD_S, _wait_boot_attached) in front of the producer's first pass, and this test (2026-09-03) polls 5 s for that pass, so alone it failed on "a judge pass is in flight" (1 failed, 1 error in 10.9 s). The defect is a condition, not a frequency: _BOOT_ATTACHED (kernel/kernel.py:30789, set at :30860) is a one-way, process-wide latch, never cleared, and the test patches km._sdk to lambda: None, so it can never latch it itself; the test passes if and only if something earlier in the same interpreter already latched it, and fails otherwise after the 8 s hold against its 5 s deadline. Alone serially: always red. The module serially: green (its alphabetically first test's _pusher_cycle() reaches _sdk() and builds an SdkBackend whose boot reconcile latches it as a side effect). The module under -n 9: red. A full -n 10 sweep: a prior latcher in the target's worker is likely but not guaranteed: five full sweeps checked on 2026-09-21 did not fire it (those for 853, 862 twice and 887, and 781's at c7e51ae47), one did (box 2's control at 65f1895f6). An isolated-level certainty and a sweep-level flake at the same time, decided by which tests ran before it in that worker's process; never in serial CI. The red-before measurement is the single test alone, serially. The contamination disclosure is conditional: a sweep carried the leaked loop only if this test's failure line is in its pytest log, which is checkable per sweep. The failed assertion skipped the stop on the body's tail and tearDown only cleared the flag, so an unpatched judge loop ran for the rest of the worker's life; the T282 census named it and could not stop it. Upstream carries the same test and the same hold; this fix was NOT run upstream (unverified there).

The blast radius, proven by romp-manager's probe (2026-09-21), has two figures with different meanings. Reach: the leaked loop runs _compact_goal_stores() on its 3 s backstop (_producer_wake.wait(3)), globbing jd.GOALDIR and rewriting any store whose mtime moved; km.jd is the one process-wide judge module (kernel/kernel.py:52, jd = load_source("romp_judge", ...): one object per interpreter), and 141 test modules call jd._rebind_state(), so the leaked loop follows jd.GOALDIR to wherever the latest rebind put it: any of those 141 scheduled after the failure in the same worker (a store saved under a private sid with a cleared root was archived 7.5 s later by the leaked thread). Visible set: 13 modules save stores with cleared roots and 18 assert on the archive; that is where a wrong result would surface, a spurious pass as well as a spurious failure in a module that did nothing wrong, and the spurious pass is the dangerous direction. 13 is not the exposure; 141 is the reach. Not determined, carried: whether the leaked loop produced flakes in earlier sweeps. The SdkBackend side-effect build is benign on its own (its orphan reap is gated on its own empty registry; sweep_dead_test_roots removes only romp-tests-* roots whose marker names a dead pid).

Measured in a hermetic scope with a 17-byte TMPDIR (the second pass, at 2d3dfc7d2): the target alone 1 failed, 1 error in 10.94 s before (at 65f1895f6), 1 passed in 0.19 s after; the module serially 9 passed in 0.28 s before, 10 passed in 0.81 s after; the module under -n 2 --dist load 10 passed in 1.01 s; the leak case alone 1 passed in 0.71 s; the leak case with a planted self.fail after tail.run(res), in a copy, 1 failed and 0 errors in 0.73 s (before this pass's cleanup registered ahead of the nested run: 1 failed and 1 error in 5.75 s, the producer and its two tiers left behind); tests/test_thread_stop_census.py 23 passed in 25.94 s (948 modules read, 408 start rows: 186 loop, 22 waits, 200 bounded; 0 tail-only among the pinned kinds, 0 unreadable receivers, 0 stale allow entries, 68 bounded tail-only excused; 19 planted shapes); tests/test_judges_process.py, tests/test_kernel_parked_ops_lock.py, tests/test_ws_send_bounded.py and tests/test_ledger_unproved_reads.py 82 passed in 5.59 s; after their site fixes tests/test_host_transport.py 104 passed, 1 skipped in 35.17 s and tests/test_sdk_stream_survives_handler_errors.py with tests/test_ws_send_bounded.py 62 passed in 2.91 s.
