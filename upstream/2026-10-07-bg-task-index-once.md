build_session called _task_outputs_for once per user turn, and every task-notification reminder in it ran a full every-task scan (_bg_scan_all_cached, which returns fresh copies of every task row) plus a linear search for the reminder's task id. Each notification is its own user turn, so the scans grow with the notifications: one whole-history build of a large session ran 2,148 of them. build_session now hands one id -> command dict to every _task_outputs_for call of a build. The first scan that answers with rows fills it, at a task notification; the first row with an id wins (setdefault, as next() did); a missing id or a row without a command reads ''; an empty answer is not kept, so after a failed read (which folds to an empty answer) the next reminder reads again, as before; and a caller passing no index runs the old search. The dict holds commands, never rows, and lives only as long as the build. The one difference, stated in the docstring and pinned: an answer that changes during the build (a record appended that a later reminder needs, the transcript rewritten or its fold state replaced, a later read failing) reached the build's later reminders under the old search and now reaches a notification only when a later build joins it again: the next build for a turn this build left unsealed, the next full build (a fold demotion or a restart) for a turn it sealed into the fold prefix, which keeps the answer it was joined with, as a sealed turn did under the old search.

The tests: tests/test_chat_fold.py TaskOutputsOneScanPerBuild builds synthetic sessions (several tasks, a launch id recorded twice, an id notified twice, two notifications in one record, unknown ids with and without an output file, a task with no command, no notifications, and a task added between two builds) and compares the whole payload with a build that takes the old search, beside expected outputs written out from the fixture. It pins the build's every-task scans as absolute counts, inside _task_outputs_for and over the whole build (one of each for six notifications, none with no notification), so a scan added anywhere in the build fails it, and it holds the difference above with the real trigger: a cold every-task fold healed during the build, after the index is taken. On the fork's main it fails on the scan count inside _task_outputs_for (6 for six notifications, where it asks for 1); tests/test_kernel_bg_tasks.py TaskOutputsIndexPerBuild, which pins the index against scripted scan answers, fails there on the new parameter. Offline bench of one 321 MB session's whole-history build, main and branch builds interleaved in one process (six runs of 6 to 8 rounds, the every-task fold warm and cold): about 1.6 to 2.5 s off a 5.9 to 8.2 s build (-24 to -31%), the branch faster in every paired round; scans per build 2,149 to 2; the task outputs identical on all 1,911 events that carry them. Tier fix: a cost defect, with a test that fails before the change.

The project's public main (last updated 2026-09-24) has the same per-reminder scan: its _task_outputs_for runs the next() search over _bg_scan_all_cached for every task notification, and its build_session calls it once per user turn. Its tests/test_chat_fold.py and tests/test_kernel_bg_tasks.py carry the harnesses the new tests use (not run against that tree).
