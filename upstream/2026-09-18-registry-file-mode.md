Upstream has the same writers byte for byte: write_reg publishes sdk/<sid>.json through a write_text temp at the umask mode (0644, or 0664 under umask 002; at the round-1 probe on 2026-09-18, on the box the fix was developed on, every live registry file and the parked-ops mirror were 0664 under the 0700 state root, while the remotes file, notify-prev, the push files, the serve token, the flag-settings files, spawn.json, the login records and the Codex registry were owner-only) and _save_pending_ops mirrors a parked ("env", {...}) op through _atomic_write with no mode, so a per-session env value under a token-shaped name sits in both files at that mode; the sibling writers of the same values (flag_settings_path, host_transport.write_spawn_spec) publish 0600 but tightened a pre-existing looser file only after the write. Every one of these writers now sets 0600 on the descriptor before the first write (os.fchmod, the shape cli/perf_export.py and the Codex registry lock already use, and like them closes the descriptor when fchmod raises): exact under any umask, no window with the text at a wider mode. The registry writer and every _atomic_write caller (the mirror, the alias migration's reg rewrite and the rest) publish through a writer-unique temp and os.replace, so the mode lands on a fresh inode, an older file tightens on its next write, and a descriptor another uid held on the old inode reads nothing new; two writers, flag_settings_path and write_spawn_spec, rewrite the published inode in place (O_TRUNC on the path, no os.replace), so their tightening is not retroactive for a descriptor another uid opened while the file sat at its old looser mode, which reads the new env block through it. That road is closed today by the 0700 state root (and for spawn.json its own 0700 directory) and is not retrofitted here. A file never written again keeps its mode behind the owner-only root, and no boot-time re-mode is added (the reviewer's call); the root's own mode was best-effort (kernel/judge.py's mkdir and chmod at import swallow OSError), and since review round 2 it is read back after the attempt and said once on stderr, naming the path and the mode read, when it is not 0700. Every reader is the same uid. A mitigation behind the 0700 state root, not a fix for the value living in a file. Found in PR 776's review round (kernel-1, extra5-2) and deferred to its own fix; review round 1 of PR 789 replaced the first cut's exclusive create at the mode (a leftover temp became an error and the mode passed through the umask) with the descriptor shape; review round 2 (2026-09-19) closed the descriptor leak on a raising fchmod at all four sites (unbounded at the mirror, whose failed save is swallowed and retried at every mutation), replaced the docstring's grep recipe for the mode-bearing caller list with an ast-walk test, and added the root-mode line.
