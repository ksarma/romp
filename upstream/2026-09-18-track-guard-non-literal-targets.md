The Bash-side track guard (a PreToolUse hook on the Bash tool) blocked a shell write to a tracked file only when the target path was literal in the command: a cp whose destination was a shell variable, a command substitution, a backtick, a ~user, a brace list past the cap, or a glob it could not expand went through and overwrote the tracked file with no change recorded, while the same command spelled out was refused (a research session reported it through the box admin, 2026-09-17). The hook now refuses such a target while a project that tracks anything is in play (the session cwd, the directory a cd moved to, or the folder a copy lands in has a .trackchanges/config.json whose tracked list holds an entry the literal rule could refuse), with a message that says the target is not literal, that a tracked file takes its change through track-edit, and to spell the path out or write outside the project; it reads no variable the command names to resolve the word (of the environment it reads HOME, for `~` and a leading `$HOME`, and the CLIs' root override, for a directory under it; only HOME's value can appear in a refusal, as a path resolved through it, and the override is named by its variable). The round-1 review (2026-09-18) bounded the rule and rounds 2 and 3 (2026-09-19) corrected it by execution: a target whose only expansions are `$$` or `${$}`, the shell's process id, at an absolute path outside every project in play is allowed, and nothing else is (round 1 listed `$RANDOM`, `$SECONDS` and `$BASHPID` as read-only; round 2 dropped BASHPID, which zsh leaves assignable; round 3 measured `unset RANDOM`, `local RANDOM=` and zsh's `typeset -h` carrying a path onto a tracked file, so a `log.$RANDOM` inside a tracked project is refused in every shell, a deliberate false refusal recoverable in one step); the project the target's own literal prefix sits in is asked first, from any cwd, for every target the hook cannot read that it can place, absolute or relative (round 3: a variable's spelling and a relative numeric one reached another project's tracked folder from a cwd in no project); a numeric target's literal directory part is resolved through the filesystem, an existing entry its number could spell is followed, a fold that leaves no expansion is judged by the literal rule, and a `..` after an existing directory climbs from that directory's real path for a literal path too (round 3 overwrote a tracked file through each of those); a copy's landing folder counts only when a tracked file could land there or holds more than 2000 entries (a deliberate false refusal, escalated; the same cap now covers a numeric name in such a folder), and a landing folder no project claims counts when an entry of it is or leads to a tracked file; a numeric name in any folder where a tracked file could land (`<root>/x-$$/y.md`, `<root>/docs/build-$$.log`) is refused from any cwd while its literal spelling may pass, the refusal naming the unknown folder when the expansion names one and offering a literal folder name or a write outside the project (round 2's addendum ruled the first-segment case; round 3 restated the class as the landing gate on the literal directory part, at any depth, and replaced a remedy that asked for the name the shell would give); a literal relative target after a `cd` the hook cannot follow (a name the shell fills in, `cd -`, `popd`, a cd inside an if or loop body, or one to a directory the command cannot enter at check time) is refused with that reason while the session's project is in play, where before it was dropped; `$'...'` is ANSI-C quoting in bash and zsh and a literal dollar is literal, so a folder or project whose name holds a dollar is judged by that name; `bash -O` and option clusters holding `o` or `O` take their word; a command nested past 64 substitutions or brace lists is marked opaque rather than overflowing the stack (evaluate read the overflow as allow); a directory is judged under its real path and its name, and `install -d` writes no file; a `$(date)` in a log's name is still refused, a stated cost, and so are a relative `$$` name from a cwd in a project and a `mkdir -p x && cd x && cmd > log` from a tracked cwd. Found on the way: a redirection onto several glob matches or brace alternatives was read as the ambiguous redirect bash refuses, but zsh (multios) writes each, so the hook now names each. Literal targets keep their verdicts; commands with no tracked project in play are untouched. Tests in tools/romp-track-bash-guard.test.mjs, the shapes module, the plan pins and the vendored skill patch 0009.
