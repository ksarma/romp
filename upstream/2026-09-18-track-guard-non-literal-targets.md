The Bash-side track guard (a PreToolUse hook on the Bash tool) blocked a shell write to a tracked file only when the target path was literal in the command: a cp whose destination was a shell variable, a command substitution, a backtick, a ~user, a brace list past the cap, or a glob it could not expand went through and overwrote the tracked file with no change recorded, while the same command spelled out was refused (a research session reported it through the box admin, 2026-09-17). The hook now refuses such a target while a project that tracks anything is in play (the session cwd, the directory a cd moved to, or the folder a copy lands in has a .trackchanges/config.json whose tracked list holds an entry the literal rule could refuse), with a message that says the target is not literal, that a tracked file takes its change through track-edit, and to spell the path out or write outside the project. What it reads to resolve a word (since B2, 2026-09-19, and the readability rule that followed; the clause here said until round 5 that it read no variable the command names, and that only HOME's value could appear in a refusal, both false since B2): a name the command itself sets to a plain string, at the top level in plain sequence and through no other construct (a tilde opening the value, a declaration flag that transforms it, a nameref, a name the shell fills in, a body, a subshell, a pipeline, a piped group, a wrapper's argument, a function call or a subscript leaves it unreadable), HOME, PWD, OLDPWD, `~+` and `~-`, none of the three once the command names the name outside an expansion or may fill it in; the resolved path is judged by name, so a refusal can show a value the command's own text set, or PWD and OLDPWD from the guard's own directory model. Of the environment it reads HOME alone (for `~` and a leading `$HOME`, as the shell does), TRACKCHANGES_ROOT, the CLIs' root override, for a directory under it, and ROMP_SID; the only environment value that can appear in a refusal is HOME's, as a path resolved through it; TRACKCHANGES_ROOT is named by its variable, never by its value, and ROMP_SID is never printed. The round-1 review (2026-09-18) bounded the rule and rounds 2 and 3 (2026-09-19) corrected it by execution: a target whose only expansions are `$$` or `${$}`, the shell's process id, at an absolute path outside every project in play is allowed, and no other expansion is numeric (round 1 listed `$RANDOM`, `$SECONDS` and `$BASHPID` as read-only; round 2 dropped BASHPID, which zsh leaves assignable; round 3 measured `unset RANDOM`, `local RANDOM=` and zsh's `typeset -h` carrying a path onto a tracked file, so a `log.$RANDOM` inside a tracked project is refused in every shell, a deliberate false refusal recoverable in one step); the project the target's own literal prefix sits in is asked first, from any cwd, for every target the hook cannot read that it can place, absolute or relative (round 3: a variable's spelling and a relative numeric one reached another project's tracked folder from a cwd in no project); a numeric target's literal directory part is resolved through the filesystem, an existing entry its number could spell is followed, a fold that leaves no expansion is judged by the literal rule, and a `..` after an existing directory climbs from that directory's real path for a literal path too (round 3 overwrote a tracked file through each of those); THE RESIDUAL PROPERTY. The guard refuses a write only when it resolves the command to a writer it models (the writer cases of extract's switch, a write redirection, an interpreter's write call it scans) reached through a road it reads (the wrapper set, the shells' script roads, the readings of the resolver, the alias and hash roads), with a target it can place or cannot read. Every write that still reaches a tracked file is one the guard does not resolve to such a writer through such a road, whether or not its text stands in the command, and falls in one of these classes, each measured by execution in tools/romp-track-bash-guard.test.mjs (THE RESIDUAL TABLE, whose rows are the population this statement is over): a writer outside the model, a program, or a write form of a program the hook models, that writes the file by its own nature and is not among the write forms the hook reads (rsync, patch, tar -x, ed, ex, vim, make, shuf -o, gawk -i inplace, awk's print redirect, uniq, scp, openssl -out, shred, curl -o, wget -O, find -exec, a git alias or a subcommand that writes the tree, bash's history -w, zsh's sysopen and mapfile modules, sed's e command and a w command in a sed script the resolver cannot read, busybox's applets); a reader outside the roads, a program that runs a command or a script the hook does not follow into it (xargs, an interpreter's system, exec or subprocess call, a wrapper outside the set, a shell outside SHELLS, a file the command writes and then runs or sources); a command name the resolver never reads, a command whose name is an expansion of a kind the resolver does not read ("$@", $1, $*, "${a[@]}", a loop variable, a name read, printf -v or a nameref filled, ${SHELL}, a substitution outside the output model such as $(which cp), a ${...} operator form the resolver does not read); a script held in a variable, a value the command gives a name through a construct the resolver does not read (`read`, `printf -v`, a positional parameter), run as a command or handed to a shell (`$c` after `read c`, `eval "$1"`, `bash -c "$c"` after `printf -v c`;
