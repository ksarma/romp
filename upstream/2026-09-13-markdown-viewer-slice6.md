Upstream ships the same viewer, the same Files pane, the same todo surfaces and the same landing shell, so every item applies there once the slices before it have landed: a file opened in the viewer takes the keyboard, so the arrow keys, PageDown and Space scroll it with no click first while a box the person was typing in keeps the keyboard; an Outline button above a rendered note lists its headings by depth and a pick puts the heading at the top of the view, opening a closed fold around it; a note left and reopened, in the same page or from the Files pane's Recent list across a page load, comes back to the place it was read, by the top block's source span with the pixel count as the fallback and never a word of the file in the store; a todo's `docs/report.md:12` or `docs/report.md#results` opens the file at that line or heading from the chat's todo card and from the Waiting-on-you pane, in the document or through the Files pane, where before the target stayed prose, and a section the file does not have is named in the notice bar rather than a silent open at the top; and a file that changed on disk while the Comments panel was closed says so above its text the next time the window has the focus or the tab is visible again, with a Reload that keeps the place. Built as Slice 6 of plans/markdown-viewer.md on Slice 8's head (fork PR 752, 2026-09-12-markdown-viewer-slice8), so the offer stacks on the six slices before it, each with its own entry (Slice 1 #390, Slice 2 #396, Slice 3 #407, Slice 4 #707, Slice 5 #749, Slice 8 #752). The files it changes are the viewer's own and the ones those entries already name: file-view.ts, the sheets' viewer regions, files.ts, files-recent.ts, path-links.ts, render.ts's openPath and todo walks, waiting.ts and the tests beside them travel with the viewer candidates; the guide and the plan port as they are. The store format is untouched (the Recent row's `place` is a field of the Files pane's own localStorage entry, validated on read and dropped when malformed, never the comments store), and the kernel's Python is untouched: the two lines that change in kernel.py are the landing shell's JavaScript, where the viewFile relay's two forwarders rebuild the message field by field and now copy `at`, so a deployment reads the field only after its kernel restarts. The `line` and `frag` options of openFileView are replaced by the one `at` option (`{ line } | { offset } | { heading }`), not aliased, so a host that passed either moves to `at`; the four callers in this repo moved with it.

2026-09-14, the PR review's round 1 (fork PR 753, the manager's review): the field the viewFile relay carries differs from upstream's twin, so the offer needs the mapping and an inbound fold the same rule. Upstream's relay carries `frag`, a string, the section a `path#slug` link names (upstream's T351): render.ts's `openPath(path, sid, ev, frag)` posts `frag: frag || null`, the landing shell's Files pane forwarder copies `frag:m.frag||null`, files.ts's `openHere(path, sid, identity, frag)` opens `{ frag }`, `openFileView`'s options are `{ line?, frag? }` and `initFileView`'s relay type reads `frag?: unknown`. The fork carries `at`, an object, at the same hops: `openPath(path, sid, ev, at)` posts `at`, both forwarders copy `at:m.at||null`, `openHere(path, sid, identity, todoId, at)` reads `readAt(m.at)` and opens `{ todoId, at, place }`, `openFileView`'s options are `{ todoId?, at?, place? }` and the relay type reads `at?: unknown`. The mapping: a `frag` string is `at: { heading: frag }` and back; a null `frag` is a null `at`; the fork's `{ line }` and `{ offset }` arms have no upstream field (upstream's `line` option is in-process, fed by no relay), and upstream has no feed-branch forwarder, the fork's being fork-only. For the offer: the port replaces `frag` with `at` at every hop named, a `frag` string becoming a heading target. For an inbound fold: an upstream change to a `frag` hop lands on the fork's `at` hop at the same place, read through that mapping, and a new upstream reader of `frag` becomes a `readAt(m.at)` reader whose heading arm carries the string. The round's other fixes are named in the `where:` line and recorded in the plan's Manager review round 1 paragraph.
